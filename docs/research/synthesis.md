### 8.4 Write ourselves (no acceptable source exists)

1. **`ThreadedVecEnv`** implementing the Section 3 architectural law: worker threads call C only (`mj_step(m, d, nstep=decimation)`, raw `qpos`/`qvel` memcpy at a measured 0.09 us per env-step), all observation assembly, reward math, and termination logic vectorised on the main thread across the whole batch. Nothing in the ecosystem does this; every existing vec-env runs per-step Python inside the worker, which is exactly what caps the published MuJoCo threading numbers at 6.3x.
2. **`mujoco_engine.py`** against MimicKit's `Engine` ABC.
3. **Procedural terrain generator and curriculum** driven by in-place `m.hfield_data` writes, plus the `mjr_uploadHField` render-sync path (Section 7).
4. **Multi-waypoint course task and goal observation.** LocoMuJoCo has only root-velocity goals; Playground has none. MimicKit's `task_location_env.py` is a single-target task and is the closest starting point.
5. **AMP discriminator in the paper's form**, replacing MimicKit's shipped BCE variant (see conflict C9 in Section 12).
6. **Terrain-safe discriminator observation** (drop root world-z, or replace it with height-above-terrain).
7. **Checkpointing, evaluation harness, video export, dashboard wiring.**

## 9. Risk Register

Ranked by expected cost to the schedule, not by probability.

| # | Risk | Evidence it is real | Mitigation | Early warning signal |
|---|---|---|---|---|
| **R1** | **AMP adversarial collapse.** Discriminator wins, style reward pins to ~0, policy stops improving or degenerates into a jitter that fools D. | AMP's own ablation ([arXiv:2104.02180](https://arxiv.org/abs/2104.02180)) names gradient penalty as the most vital stabilizer, which is an admission that the vanilla objective is unstable. | Bounded LSGAN reward `r = max(0, 1 - 0.25(D-1)^2)` rather than the unbounded BCE/softplus form. GP on **real data only**, applied to the **normalized** observation, `w_gp=10`. Policy replay buffer (1e5, `keep_prob` 0.01). Logit L2 reg 0.01. Separate discriminator optimizer at its own LR (1e-5) so it is independently tunable. Build DeepMimic single-clip tracking **first**. | Log D's accuracy on agent vs demo batches every iteration. **Anything above 0.85 sustained for 50 iterations is the trigger.** Second signal: mean style reward falling below 0.05 while task reward is flat. |
| **R2** | **Discriminator learns terrain, not style.** Once Phase 4 lands, root world-z in the AMP observation becomes a "where am I on the hill" detector that separates policy from flat-ground mocap with zero style content. Same class of bug: `localRootObs=False` makes style heading-dependent, which is fatal for a waypoint policy. | The shipped Isaac `HumanoidAMPPPO.yaml` has `localRootObs: False`. Every clip in every accessible dataset was captured on flat ground. | `localRootObs = True`, always. Drop `root_h` from the 105-dim frame, or replace it with height-above-terrain sampled from the hfield under the root. Freeze the discriminator observation spec before Phase 4 starts and assert its dimensionality in a unit test. | Style reward **drops sharply the moment terrain amplitude increases**, while tracking error is unchanged. Diagnostic: hold the policy fixed, raise terrain amplitude, and watch D's agent-accuracy climb. |
| **R3** | **GIL ceiling erodes as env logic grows.** Every scalar Python or pybind call added to the per-step path is multiplied by the batch and serialised. | Measured on this machine: 4 `mju_rotVecQuat` pybind calls cost **23.78 us**, scalar numpy reward math **13.37 us**, versus 0.09 us per env-step for a raw state memcpy. Full vec env 82,308 steps/s vs physics-only ceiling 100,908 steps/s. Independently, the MuJoCo researcher measured a *realistic* Python-in-worker loop peaking at 6.31x on 8 threads and **degrading** past that. | Architectural law, enforced by review: workers call C only. Anything that looks like a per-env loop becomes a batched numpy op on the main thread. Terrain height queries are array lookups into our own heightmap, never `mj_ray`. | A CI throughput test that fails the build if full-vec-env throughput drops below **70,000 env steps/s** on the Phase-1 model. Watch the ratio (full env) / (physics-only) and alert below 0.75. |
| **R4** | **Phase-3 model swap throughput cliff.** All headline numbers are for `humanoid.xml` at nq=28 nv=27 nu=21. The MimicKit target model is nq=35 nv=34 nu=28 with box feet, which means more contact points per foot. | The MuJoCo researcher warns plainly: a realistic humanoid with more geoms and contact pairs runs "2-5x lower throughput" and the stock figures should not be used to size a training budget. | Benchmark B2 before Phase 3 starts, not during. Levers in order of preference: raise decimation from 4 to 5, reduce `n_envs`, simplify non-foot collision geoms, cap solver iterations (measured to be nearly free either way, so this is a weak lever). Budget the AMP run against the **measured** post-swap number. | B2 returning under 40,000 env steps/s in the full vec env. Secondary: mean active contacts per humanoid above ~20 on flat ground. |
| **R5** | **Heightfield cost and render staleness.** Terrain contact cost was only ever measured with a single sphere. Separately, mutating `m.hfield_data` updates physics but **not** visuals until `mjr_uploadHField` runs against the renderer's GL context, which is reachable only via the private `renderer._mjr_context`. | Verified by the MuJoCo researcher: zero pixel change without the upload call. `renderer._mjr_context` is not public API and can break across releases. | Benchmark B3 sweeps resolution x amplitude before committing. Construct and hold our **own** `mujoco.MjrContext` rather than reaching into the Renderer's private attribute. Add a pixel-diff assertion in the video test. macOS OpenGL is legacy (CGL requests OpenGL 2.1, and `ARB_clip_control` is unavailable, so `mjDEPTH_ZEROFAR` accuracy is degraded), so do not design any depth-image observation. | Terrain-curriculum videos showing flat ground while the reward curve says otherwise. Throughput on 128x128 hfield below 60% of flat ground. |
| **R6** | **Mocap availability and licensing.** MimicKit's `data/motions/` is **empty on clone** and gated behind a manual SharePoint download. AMASS, SMPL, SMPL-X and MANO each need a separate Max Planck account and are non-commercial. LAFAN1 is CC BY-NC-ND, whose NoDerivatives clause arguably forbids redistributing retargeted versions at all. | Verified: MimicKit repo contains `humanoid.xml` but no motion data. | **Day one is registration-free by construction**: dm_control's pre-fitted CMU HDF5 ([verified HTTP 200 today](https://storage.googleapis.com/dm_control/cmu_2020_dfe3e9e0.h5), ~477 MB, `last-modified` 2020-07-15) plus LocoMuJoCo's 19 HuggingFace clips (`walk`, `walkturn`, `stepinplace1-3`, `highknee`, ...). [100STYLE](https://zenodo.org/record/8127870) (CC BY 4.0, no registration) is the commercially clean corpus if the project ever leaves personal research. Pre-fetch and checksum the HDF5 into the repo setup step. | The setup script's checksum step failing, or a 4xx from `storage.googleapis.com`. Do not discover this mid-training. |
| **R7** | **Retargeting artifacts invalidate imitation.** Foot skate, ground penetration and impossible joint angles in the reference make the discriminator learn artifacts as "style", and make DeepMimic tracking unlearnable. Related: the SMPL humanoid MJCF has `range="-180 180"` on **every one of its 69 hinges**, so it has anthropometric proportions and no anatomy. | Reported directly in LocoMuJoCo [issue #88](https://github.com/robfiras/loco-mujoco/issues) (abnormal foot behavior with SkeletonTorque on AMASS, 2025-12-18). | Build order forces this out early: DeepMimic single-clip tracking converges in ~7.4M samples (minutes on this machine) and will not converge at all if the retarget is bad. Play back every clip kinematically and assert min foot height > -1 cm and per-frame foot horizontal velocity below a threshold during stance, before any RL runs. Prefer the pre-fitted CMU HDF5 precisely because DeepMind already did the fit. | DeepMimic tracking failing to converge on a single clip, or the playback assertion firing. |
| **R8** | **MPS is a beta backend, and it can lie about being present.** [Issue #177819](https://github.com/pytorch/pytorch/issues/177819): under a seatbelt sandbox, `torch.backends.mps.is_available()` returns **False** with no GPU access, so a benchmark run by an agent silently measures CPU and produces misleading numbers. Silent numerical-corruption bugs are still being filed as of July 2026: [#189960](https://github.com/pytorch/pytorch/issues/189960) (`torch.cat` integer overflow past 2^31 elements, writes out of bounds), [#189690](https://github.com/pytorch/pytorch/issues/189690) (`non_blocking` CPU-to-MPS copy reads released storage). | Both open as of the dossier. | Hard assert `torch.backends.mps.is_available()` at process start and refuse to run (benchmark B9). **Never** use `non_blocking=True` on MPS copies. **Never** enable `PYTORCH_ENABLE_MPS_FALLBACK=1` outside bring-up, so silent CPU round-trips cannot hide. `float32` only, never `float64` (unsupported on MPS and raises). Run the MPS-vs-CPU parity gate (B8) on every op in the actor, critic and discriminator. Do **not** plan on `torch.compile`: tracker [#150121](https://github.com/pytorch/pytorch/issues/150121) is still an open "early prototype", 3 of 33 items done as of 2026-06-02, with a confirmed silent-wrong-answer bug ([#169738](https://github.com/pytorch/pytorch/issues/169738)). | B8 reporting any op with relative error above 1e-3. A run whose loss diverges on MPS but not on CPU with the same seed. Any benchmark that reports MPS throughput suspiciously close to the CPU figure. |

**Watchlist (below the top 8, but worth a tripwire):** dependency rot from MuJoCo's fast minor cadence (3.10.0 removed `mjthread.h` and renamed `efc_diagApprox`; pin exactly and read the changelog before every bump). Seeded runs on MPS are not bit-reproducible, so the reproducibility story is "same machine, same seed, documented tolerance", not "bitwise". `dm-control` does not install on Python 3.13 ([issue #511](https://github.com/google-deepmind/dm_control/issues/511)), which pins our interpreter for the foreseeable future.

### 10.2 Open questions the Phase-0 script must settle

| ID | Question | Procedure | Metric | Decision rule |
|---|---|---|---|---|
| **B1** | Optimal worker-thread count for the **full** vec env, and whether the 4 E-cores stay free | Sweep threads in {6, 8, 10, 12, 14} at fixed `n_envs=4096`, C-only workers, 60 s steady state each. Create worker threads at default QoS (macOS schedules these to P-cores) and pin nothing else. Record wall clock and, separately, `powermetrics` E-cluster residency in a manual run. | env steps/s; E-cluster active residency % | Pick argmax throughput. **If 10 threads is within 3% of peak, choose 10** and leave the E-cores for the main-thread numpy and the Metal command queue. If throughput at 12 or 14 exceeds 10 by more than 8%, take it and document that we are oversubscribing. |
| **B2** | Cost of the Phase-1 to Phase-3 model swap | Same harness, flat ground, chosen thread count. Model A: MuJoCo `humanoid.xml` (nq=28). Model B: MimicKit `humanoid.xml` (nq=35, box feet). Record mean active contacts. | env steps/s; contacts/humanoid | If B >= 60,000: proceed unchanged. If 40,000 to 60,000: raise decimation to 5 and re-measure. **If below 40,000: simplify non-foot collision geoms before Phase 3 begins**, and re-scope the AMP sample budget against the measured rate. |
| **B3** | Heightfield contact cost | Model B on hfield at resolution {64, 96, 128, 256}^2 x amplitude {0.02, 0.05, 0.10, 0.20} m, chosen thread count. | env steps/s as a fraction of B2 flat-ground; mean active contacts | **Choose the highest resolution that retains >= 60% of flat-ground throughput at 0.10 m amplitude.** If 128 fails that bar, drop to 96. Amplitude is a curriculum variable, so record the throughput/amplitude curve and use it to bound the curriculum's top end. |
| **B4** | Terrain variant count and reshuffle cost | Each worker thread owns V `MjModel` instances (V terrain variants), envs bound to one. Sweep V in {1, 2, 4, 8}. Time: (a) writing a fresh 128x128 heightmap into `m.hfield_data`, (b) a full batch reset with `mj_setState(mjSTATE_FULLPHYSICS)`. Record RSS. | ms per full terrain reshuffle; MB resident | If a reshuffle costs **> 1% of one PPO iteration's wall clock**, stop regenerating per episode and instead pre-generate V variants and rotate. Target total variants = threads x V >= 64 for curriculum diversity. Reject any V whose RSS exceeds 24 GB (we have 96 GB but the Metal working set is capped at ~83 GB). |
| **B5** | PPO shape: envs x minibatch on MPS | Grid `n_envs` in {1024, 2048, 4096, 8192} x minibatch in {256, 1024, 4096, 16384}, 4 epochs, 50 iterations each, Model B. | end-to-end env steps/s; gradient-updates/s; iteration wall clock split into rollout / update | Maximize **end-to-end env steps/s**, not update throughput. This must beat the current 60,888 baseline or we keep the baseline config. Report the rollout/update split so R3 regressions are attributable. |
| **B6** | AMP discriminator overhead inside the real loop | Iteration wall clock with disc disabled, then enabled at disc batch {256, 1024}, including gradient penalty (`create_graph=True`) on real data only. | % iteration overhead | **Accept up to 25%.** Above that, drop disc batch to 256 (the paper's own value) before reducing update frequency, because the paper's config is already the CPU-scale config. Above 40% even at batch 256, profile the GP backward specifically. |
| **B7** | Concurrency holds under real load | Run B5's best config. Measure physics-thread throughput (i) with the MPS update running, (ii) with it stubbed out. | ratio of (i) to (ii) | **>= 0.85: proceed.** Below 0.85: double-buffer so rollout for iteration k+1 overlaps the update for iteration k, then re-measure. If still below 0.85, drop worker threads by 2. |
| **B8** | MPS vs CPU numerical parity gate | For every op in the actor, critic and discriminator forward and backward, run identical fp32 inputs on both devices. Then run 100 seeded PPO iterations on a tiny config on each device and compare mean-return trajectories. | max relative error per op; return-curve divergence | **Any op above 1e-3 relative error is pinned to CPU or replaced.** Ops between 1e-4 and 1e-3 get logged and re-tested each PyTorch bump. Return curves must stay within 2 standard errors of each other over 100 iterations. |
| **B9** | Is MPS actually present | `assert torch.backends.mps.is_available()` at process start, before any timing. | boolean | **Hard failure with a message telling the operator to run from a real Terminal, not from an agent sandbox.** This exists solely because of [pytorch#177819](https://github.com/pytorch/pytorch/issues/177819), where a sandboxed process reports `is_built()=True, is_available()=False` and would silently benchmark CPU. |
| **B10** | Video path and terrain render sync | Offscreen render at 640x480 through our own `MjrContext`. Regenerate `hfield_data`, call `mjr_uploadHField`, assert the rendered frame changed by a pixel-diff threshold. Then assert it does **not** change when the upload is skipped. | render fps; pixel-diff pass/fail | Both assertions must pass. If `mjr_uploadHField` cannot be driven from our own context, fall back to `renderer._mjr_context` and add a version-pin comment plus a test that fails loudly on the next MuJoCo bump. Render fps below 30 at 640x480 means videos move to a separate offline pass. |
| **B11** | MLX fallback tripwire (re-run, do not decide now) | Re-run the end-to-end per-iteration comparison after Model B and AMP are both in, since the current 1623 vs 1670 ms result predates both. | ms per PPO iteration, MPS vs MLX | **Switch only if MLX is more than 20% faster end-to-end on two consecutive independent measurements.** A microbenchmark win does not qualify: MLX's measured 12x advantage on the numpy-to-device hop and 20-25% on the isolated update step did **not** survive to end-to-end (conflict C3). |
| **B12** | Determinism envelope | Same seed twice, 50 iterations, on CPU and on MPS. | max divergence in mean return | CPU must be bitwise identical. ### 11.5 Explicitly not installed

`jax`, `jaxlib`, `mujoco-mjx`, `jax-metal`, `jax-mps`, `warp-lang`, `mujoco-warp`, `newton`, `playground`, `brax`, `isaacgym`, `rl-games`, `rsl-rl-lib`, `skrl`, `torchrl`, `tensordict`, `stable-baselines3`, `smplx`, `chumpy`, `loco-mujoco` **from PyPI**.

Reasons, briefly and bluntly. **`jax-metal` is dead**: last release 0.1.1 on 2024-10-08, no public source to fork, Apple's docs never updated past 0.1.0 / macOS Sonoma 14.4, and it hard-fails at compile time on modern jaxlib on an M3 Max specifically ([jax#34109](https://github.com/jax-ml/jax/issues/34109), 2025-12-26, `jnp.arange(10)` raises a StableHLO bytecode error). **Anything CUDA-only is disqualified outright**: MuJoCo Warp, mjlab, Isaac Gym, Isaac Lab. Warp on this machine reports `CUDA not enabled in this build` with only a `cpu` device. **`mujoco-mjx` would be the worst of both worlds**: MuJoCo's own docs say single-scene MJX-JAX "can be 10x slower than MuJoCo", plus there is an open, unfixed 100x-to-2285x macOS regression on `jax>=0.7` from the new XLA:CPU fusion emitters ([mujoco#2957](https://github.com/google-deepmind/mujoco/issues/2957), [jax#33761](https://github.com/jax-ml/jax/issues/33761)), which requires an undocumented `XLA_FLAGS` workaround and still reproduces on jax 0.9.1. **`chumpy` cannot run on Python 3.12** (`from numpy import bool, int, float`, plus `inspect.getargspec` which was removed in 3.11), which is why the SMPL/AMASS path is deferred and isolated. `loco-mujoco` from PyPI is version 1.0.0 from 2025-04-17 and pins `mujoco==3.2.7` and `numpy<2.0`.

## 12. Conflicts Between the Dossier and the Measurements

Recorded so the reasoning stays auditable. **In every row, the measurement on the target machine wins.**

| # | Researcher claim | Measurement | Resolution |
|---|---|---|---|
| **C1** | "MPS per-op dispatch is ~24 us vs ~1 us on CPU, so a small PPO MLP will very likely run **slower** on MPS than on the M3 Max CPU. Benchmark CPU as a serious candidate, not a fallback." ([pytorch#148219](https://github.com/pytorch/pytorch/issues/148219)) | MPS 8,562 vs CPU 1,391 GFLOP/s (6.2x).
