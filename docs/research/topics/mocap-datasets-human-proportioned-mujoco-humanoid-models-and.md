## Summary

Nothing in this topic area is CUDA-only at the data or model level — mocap datasets are platform-neutral and MuJoCo's CPU engine is fully native on arm64, so the models all load and step on the M3 Max. The CUDA problem appears only in the *accelerated* paths: LocoMuJoCo v1.1's headline MJX/MjWarp backend requires MuJoCo Warp on an NVIDIA GPU, and jax-metal (the only Metal backend for JAX) has been stuck at 0.1.1 since 2024-10-08, so LocoMuJoCo on this machine is a single-environment CPU library only. The lowest-friction path by a wide margin is dm_control: its CMU humanoid is a 56-joint, position-actuated MJCF built from a real CMU mocap subject's ASF skeleton, and DeepMind hosts ~3.5 h of CMU mocap already fitted to that exact model as a single ~477 MB HDF5 on Google Cloud Storage — no registration, no retargeting, no SMPL license. Everything AMASS-related (AMASS itself, SMPL, SMPL-X, SMPL+H/MANO) requires a separate Max Planck account per site and is strictly non-commercial; the SMPL body models also still ship as Python-2 chumpy pickles, which do not import under Python 3.12 without a conversion step. For retargeting, GMR is the best-maintained tool (MIT, mink+MuJoCo IK, 2.6k stars) but it targets 18 *robots*, not human-proportioned models, and its README is Ubuntu-only — though every one of its dependencies ships macOS arm64 wheels. The most human-realistic model available, MyoSkeleton (151 DoF, spine, fingers, toes), is non-commercial-licensed and far too expensive to PPO-train on a laptop.

## Key facts

- dm_control's CMU mocap data is the single best find for this project: DeepMind pre-fitted raw CMU point-cloud data onto the dm_control CMU humanoid walker and hosts it as HDF5 on Google Cloud Storage with NO registration — https://storage.googleapis.com/dm_control/cmu_2020_dfe3e9e0.h5 (~477 MB) and cmu_2019_08756c01.h5 (~488 MB). Verified in dm_control/locomotion/mocap/cmu_mocap_data.py; ~3.5 hours of locomotion/acrobatics/arm motion. Zero retargeting needed.
- dm_control CMU humanoid: 56 joints (_CMU_MOCAP_JOINTS), 56 POSITION actuators (not torque), model files humanoid_CMU_V2019.xml (default) and humanoid_CMU_V2020.xml; skeleton derived from the ASF model of CMU Mocap subject #8, so proportions are a real human's. Upright pelvis height 0.94 m (V2019) / 1.143 m (V2020). Class docstring: 'A position-controlled CMU humanoid with control range scaled to [-1, 1]'. Apache-2.0.
- SMPLSim's smpl_humanoid.xml (verified by reading the XML): 24 bodies, 1 freejoint + 69 hinge joints, 69 <motor> torque actuators all with gear="1", 32 capsule + 10 box geoms, no meshes. CRITICAL WEAKNESS: every single hinge has range="-180 180" — the model has anthropometric proportions and mass distribution but essentially NO realistic joint limits.
- SMPLSim removed chumpy from the repo on 2025-06-12 (commit 'Remove chumpy from the repo', PR #14). This matters: it is the only SMPL-humanoid toolchain in this survey that is plausibly Python 3.12-clean out of the box. License BSD-3-Clause, mujoco>=3, python>=3.8, deps are all arm64-wheel-available.
- LocoMuJoCo human models, from loco_mujoco/environments/humanoids/skeletons.py: SkeletonTorque (skeleton_torque.xml, 27 torque actuators — lumbar spine, shoulders, elbows, wrists, hips, knees, ankles; 65-dim obs) and SkeletonMuscle (skeleton_muscle.xml, 106 actuators = 92 Hill-type muscles on the lower limbs + 14 torque actuators for the upper body; same 65-dim obs). HumanoidTorque/HumanoidMuscle are deprecated aliases.
- MyoSkeleton (loco_mujoco/environments/humanoids/myoskeleton.py): 151 joints, 150 position actuators with per-joint force limits 20–200 N, 313-dim observation, includes spine, articulated fingers, realistic knee mechanics and functional toes. Added in LocoMuJoCo v0.4.1 (2024-09-13). Requires running `loco-mujoco-myomodel-init` to accept the license and download it separately.
- MyoSkeleton license (myolab/myo_model LICENSE, verified): owned by MyoLab Inc.; 'Any other use, in particular any use for commercial, pornographic, military, or surveillance, purposes is prohibited.' No commercial-licensing contact is given in the file.
- Exact LocoMuJoCo AMASS setup (verbatim from loco_mujoco/smpl/README.MD): `pip install torch --extra-index-url https://download.pytorch.org/whl/cpu` then `pip install -e '.[smpl]'`; then `mkdir $HOME/amass && loco-mujoco-set-amass-path --path $HOME/amass`, `mkdir $HOME/smpl && loco-mujoco-set-smpl-model-path --path $HOME/smpl`, `loco-mujoco-set-conv-amass-path --path $HOME/amass_conv`. From https://amass.is.tue.mpg.de/index.html you must download the **SMPL-H G** variant of each sub-dataset (not SMPL-X). From https://mano.is.tue.mpg.de/download.php download the 'Extended SMPL+H model' plus 'Models & Code'.
- LocoMuJoCo's SMPL-H conversion step needs a throwaway Python 3.10 environment because it depends on chumpy: `python3.10 -m venv smplh_model_conversion_env && source .../bin/activate && pip install 'numpy<1.23.0' chumpy tqdm pyyaml && python loco_mujoco/smpl/generate_smplh_model.py --smpl-conf-file loco_mujoco/smpl/conf_paths.yaml`. The provided install_smplh.sh automates this but hard-requires conda (creates and deletes a conda env), which does not fit a uv-only setup — use the manual venv path.
- LocoMuJoCo's retargeting (loco_mujoco/smpl/retargeting.py) does NOT use mink or classical IK. It is gradient-based: torch.optim.Adam minimizing position + geodesic-rotation losses between mocap sites and SMPL joints, with mujoco.mj_step in the loop to respect joint constraints. Key entry points: fit_smpl_shape(), fit_smpl_motion(), motion_transfer_robot_to_robot(), load_retargeted_amass_trajectory(). Imports torch, joblib, mujoco, jax.numpy, smplx.lbs.transform_mat.
- GMR (General Motion Retargeting, ICRA 2026) v0.2.0, MIT, 2589 stars. IK is built on mink + MuJoCo. setup.py: python_requires='>=3.10', deps = loop_rate_limiters, mink, mujoco, numpy, scipy, qpsolvers[proxqp], rich, tqdm, opencv-python, natsort, psutil, smplx (from git), protobuf, redis, imageio. Inputs: SMPL-X (AMASS, OMOMO), BVH (LAFAN1, Nokov, Xsens), FBX (OptiTrack), PICO, GVHMR. Outputs: 18 humanoid ROBOTS (Unitree G1/H1/H1-2, Booster T1/K1, Talos, Fourier GR3, ...) — no human-proportioned / SMPL / skeleton target.
- AMASS registration is self-serve, not manually approved as far as I can tell: the form at https://amass.is.tue.mpg.de/register.php asks only for email, password, password confirmation, and three checkboxes (privacy statement, non-commercial data license, optional emails). No approval-time language appears anywhere on the page. SMPL, SMPL-X and MANO each need their OWN separate account on their own site — one registration does not cover the others.
- AMASS scale (homepage): >40 hours, >300 subjects, >11000 motions, unifying 15 optical marker-based datasets. The ICCV 2019 paper's table gives per-subset figures including CMU (96 subjects, 1983 motions, 543.49 min), KIT (55 subjects, 4232 motions, 661.84 min), BMLrub (111 subjects, 3061 motions, 522.69 min), ACCAD (20 subjects, 252 motions, 26.74 min); the growing total is ~440 subjects / 13195 motions / 2600.22 min.
- AMASS news page shows the dataset is essentially frozen: last entries are 2024-11-08 (extra MOYO motions + mp4 renders) and 2024-01-16 (MOYO yoga release). Nothing in 2025 or 2026. SMPL-X format variants were added 2022-02-14.
- CMU Graphics Lab Mocap (http://mocap.cs.cmu.edu/) needs NO registration and has the most permissive license of any dataset here: free for research, 'You may include this data in commercially-sold products, but you may not resell this data directly, even in converted form.' Funded by NSF Grant #0196217. ~2605 trials, 6 categories, 140+ subjects, distributed as C3D (raw markers), ASF/AMC and BVH.
- LAFAN1: github.com/ubisoft/ubisoft-laforge-animation-dataset, lafan1.zip ≈137 MB behind git-lfs. 5 subjects, 77 sequences, 496,672 frames at 30 fps (~4.6 h), all BVH, named [theme][take]_[subjectID].bvh. License CC BY-NC-ND 4.0. Repo last pushed 2022-09-10 (static, not abandoned-in-a-bad-way).
- 100STYLE: Zenodo record 8127870, DOI 10.1145/3522618, published 2022-05-04, CC BY 4.0 — the only large style/locomotion set here that permits commercial use. Files: 100STYLE.zip 1.5 GB (raw BVH, 60 fps, Xsens) and 100Style-Labelled-Data.zip 14.8 GB. 4M+ frames across 100 locomotion styles, each with forward/backward/sidestep walk+run, idle, and transitions. No registration.
- LocoMuJoCo's own bundled data lives at huggingface.co/datasets/robfiras/loco-mujoco-datasets — 1.97 GB, license cc-by-nc-nd-4.0, ~2951 downloads/month, auto-fetched by the library. Default and LAFAN1 sources download automatically; only AMASS is manual.
- LocoMuJoCo v1.1.0 (2026-03-10) raised the floor to MuJoCo/MJX/MjWarp >= 3.5, migrated environment construction to mjspec, and moved robot model files OUT of the main package into a separate repo (robfiras/loco-mujoco-models, last pushed 2026-03-09, 0 stars, no license file, flagged as a fork).
- PHUMA (DAVIAN-Robotics/PHUMA, Apache-2.0) is a newer alternative worth knowing: physics-curated + physics-constrained retargeted locomotion data derived from Motion-X and Humanoid-X, pre-built for Unitree G1 and H1-2, downloaded from HuggingFace via `bash download_phuma.sh`. Integrated with NVIDIA ProtoMotions in Dec 2025. Requires Python 3.9 + conda.
- Gymnasium Humanoid-v5 for reference: 17 torque actuators, action space Box(-0.4, 0.4, (17,)), 348-dim default observation, model traces back to Tassa/Erez/Todorov 2012. Cheapest to simulate but proportions and DoF are far from human — unsuitable as a gait-imitation target.
- mink v1.2.0 (2026-06-20) release notes explicitly benchmark on Apple hardware: a broadphase filter in CollisionAvoidanceLimit 'reduces collision-phase time by ~2.9x and end-to-end IK time by ~3.3x' on M1 Max. This is the strongest direct evidence in this whole survey that a core dependency is exercised on Apple Silicon by its maintainer. Apache-2.0; earlier the project swapped GPL quadprog for MIT-licensed DAQP.

## Reusable for this project

- dm_control's pre-fitted CMU mocap HDF5 — https://storage.googleapis.com/dm_control/cmu_2020_dfe3e9e0.h5 (~477 MB, ~3.5 h). Already fitted to the CMU humanoid MJCF, so it skips the entire retargeting problem, the entire SMPL registration problem, and the entire chumpy problem. Start here for Phase 3.
- dm_control's humanoid_CMU_V2020.xml + dm_control/locomotion/walkers/cmu_humanoid.py — 56 joints, 56 position actuators, real-human ASF-derived proportions, Apache-2.0. The cmu_pose_to_actuation() helper converts a target pose directly into ctrl values, which is exactly the DeepMimic/AMP PD-target interface you need. Best proportions-to-cost ratio of anything surveyed.
- dm_control/locomotion/mocap/ parsing and playback utilities — HDF5 loading, clip indexing, and a mocap-tracking task scaffold, all Apache-2.0 and pip-installed with dm-control 1.0.44.
- mink v1.2.0 as the IK layer for any custom BVH→MJCF retargeting you write yourself. Apache-2.0, MuJoCo-native (no Pinocchio), DAQP/proxqp solvers, actively maintained, demonstrably exercised on Apple Silicon. Its examples/humanoid_h1.py is a working template for whole-body site-tracking IK.
- SMPLSim's smpl_humanoid.xml and its SMPL_Robot generator class — BSD-3-Clause, chumpy-free since 2025-06-12, mujoco>=3, generates gender- and body-shape-specific MJCF from SMPL/SMPL-H/SMPL-X in capsule or mesh form. Use it if you need exact anthropometry, but you must add joint limits yourself.
- LocoMuJoCo's skeleton_torque.xml / SkeletonTorque environment (27 torque actuators, MIT-licensed code) as a mid-complexity biomechanical target between the CMU humanoid and MyoSkeleton — usable on CPU, unlike SkeletonMuscle.
- LocoMuJoCo's single-file JAX PPO / GAIL / AMP / DeepMimic implementations — MIT, clean reference implementations of exactly the AMP-style objective this project needs. Read them for the algorithm even if you run your own CPU training loop.
- LocoMuJoCo's loco_mujoco/smpl/retargeting.py as an algorithmic reference for gradient-based (Adam + mj_step) SMPL→MJCF retargeting, which is a materially different and more physics-consistent approach than pure IK.
- 100STYLE raw BVH (100STYLE.zip, 1.5 GB, CC BY 4.0, no registration) — the only commercially-clean large gait corpus here, and it is 100 *styles of locomotion* specifically, which maps directly onto a human-like-gait objective. Pair with orangeduck/100style-retarget for a common-skeleton version.
- CMU ASF/AMC + BVH from mocap.cs.cmu.edu as the license-safe fallback corpus if the project ever needs to be commercially clean (research use free, commercial products permitted, only direct resale of the data forbidden).
- keatonkraiger/SMPL_2_Python3 conversion script if you do end up needing SMPL .pkl models under Python 3.12 — but audit it first (2 stars, 2 commits, no license).
- PHUMA (Apache-2.0) if you later want physics-curated, artifact-filtered locomotion clips rather than raw AMASS — it has already done the ground-penetration and foot-slide cleanup that raw retargeting leaves behind.

## Blockers

- LocoMuJoCo's headline feature is unusable on this machine. v1.1.0 requires MuJoCo/MJX/MjWarp >= 3.5 and its speed story is MJX + MuJoCo Warp on 'compatible GPUs' — i.e. NVIDIA/CUDA. On the M3 Max you get the plain single-environment MuJoCo CPU backend only, which is exactly the slow path LocoMuJoCo exists to avoid. The library still works; the parallelism does not.
- jax-metal, the only Metal backend for JAX, is at 0.1.1 released 2024-10-08 — roughly 22 months stale as of today, and Apple's own docs call it experimental with float64/complex unsupported. Treat any JAX-GPU path (LocoMuJoCo's PPO/GAIL/AMP/DeepMimic implementations are all JAX) as CPU-only here.
- loco-mujoco on PyPI is version 1.0.0 uploaded 2025-04-17 and pins mujoco==3.2.7 / mujoco-mjx==3.2.7 and numpy<2.0. That will actively fight a modern mujoco 3.11 environment. You must install from GitHub master to get v1.1.0. Silent version trap.
- chumpy blocks Python 3.12 for original SMPL/SMPL-H/SMPL-X .pkl body models. chumpy 0.70 (2020-08-26, abandoned) does `from numpy import bool, int, float, ...` which breaks on numpy>=1.24, and calls inspect.getargspec which was removed in Python 3.11. Workarounds: (a) one-time conversion in a throwaway py3.10 venv with 'numpy<1.23.0'; (b) keatonkraiger/SMPL_2_Python3 (tested on Python 3.11.13, ships a pre-patched chumpy, but only 2 stars, no license, 2 commits, last push 2025-12-05 — read it before trusting it); (c) prefer .npz distributions where offered.
- LocoMuJoCo's install_smplh.sh hard-requires conda (it creates and destroys a conda env named smplh_model_conversion_env). With a uv-only toolchain you must run the manual python3.10 venv path from loco_mujoco/smpl/README.MD instead.
- GMR is the best-maintained retargeter but it is aimed at ROBOTS, not human-proportioned models. All 18 targets are commercial humanoid robots (Unitree, Booster, Talos, Fourier...). There is no SMPL-humanoid, dm_control CMU humanoid, or biomechanical-skeleton target. For this project it retargets to the wrong thing.
- GMR's README states Ubuntu 22.04/20.04 and Python 3.10 only, and there is not a single macOS/Apple/arm64/M-series issue in its tracker — so macOS is untested, not known-broken. Every dependency does ship arm64 wheels (proxsuite 0.7.3 has macosx_arm64 wheels for cp310/311/312; mink, mujoco, smplx are pure-Python or arm64-native), so it will probably work, but you would be the first to find out. Its perf table is CPU-only: 60–70 FPS on a Threadripper 7960X, 35–45 FPS on an i9-13900K.
- PHC is disqualified as a runnable system: it requires Isaac Gym (Linux + CUDA only), Python 3.8, and PyTorch with CUDA 11.6. Last commit 2025-08-21 and recent work targets IsaacLab. Only its MJCF assets and its SMPL-file-preparation docs are reusable. PHC_MJX (the MuJoCo port) is worse — last push 2025-02-03, 65 stars, no license file at all, so you cannot safely reuse its code.
- The SMPL humanoid MJCF has no realistic joint limits. Every one of its 69 hinges is range="-180 180". For a project whose goal is *human-like* gait, that means the policy can reach anatomically impossible poses and the reward will not stop it. You would have to author per-joint limits yourself.
- License contamination if this ever goes beyond personal research. AMASS, SMPL, SMPL-X, SMPL+H/MANO and MyoSkeleton are all non-commercial-only, and AMASS's license explicitly forbids training algorithms for commercial deployment. LAFAN1 is CC BY-NC-ND — the NoDerivatives term is a genuine problem because retargeting produces a derivative work. A policy trained on AMASS or LAFAN1 is not commercially clean.
- Human3.6M is a dead end for this project and possibly inaccessible. The site is HTTP-only (https://vision.imar.ro/... 302-redirects down to http://, which my fetcher refused), it requires account creation plus maintainer approval, and it is video/pose data rather than marker mocap. I could NOT verify it is currently reachable. Skip it.
- mocap.cs.cmu.edu has a broken TLS certificate chain — my HTTPS fetch failed with 'unable to verify the first certificate'. Direct downloads over HTTPS may need --insecure or plain HTTP, which is a practical annoyance for any automated fetch script. This is another reason to prefer the dm_control Google Cloud Storage HDF5.
- MyoSkeleton at 151 joints / 150 position actuators, and SkeletonMuscle at 106 actuators with 92 Hill-type muscle models, are both far too expensive to PPO-train on CPU-only hardware within a laptop time budget. Muscle actuators in particular add stiff dynamics requiring small timesteps. Realistic ≠ trainable here.
- AMASS per-subset download sizes in GB are NOT publicly listed — the download page is behind login and I could not retrieve the table. Plan for a manual, per-subset click-through download of ~15 archives; budget tens of GB and do not expect a scriptable bulk endpoint. (Third-party HuggingFace mirrors showing 34.2 GB / 68.1 GB exist but are unofficial re-uploads of a non-commercial dataset — do not rely on them.)
- Registration is per-site, not per-organization: amass.is.tue.mpg.de, smpl.is.tue.mpg.de, smpl-x.is.tue.mpg.de and mano.is.tue.mpg.de each need their own account and license acceptance. Budget four separate signups before any AMASS pipeline runs.

## Performance evidence

- mink v1.2.0 (2026-06-20) release notes: broadphase filtering in CollisionAvoidanceLimit 'reduces collision-phase time by ~2.9x and end-to-end IK time by ~3.3x' — benchmarked on M1 Max. Same release: ~1.3x faster IK for multi-task problems from batched QP objective assembly. https://github.com/kevinzakka/mink/releases
- GMR README retargeting throughput, CPU-only: 60–70 FPS on AMD Ryzen Threadripper 7960X; 35–45 FPS on Intel Core i9-13900K. No Apple Silicon number published. https://github.com/YanjieZe/GMR
- LocoMuJoCo v1.1.0 release notes claim MJX environments run up to 30% faster with the MjWarp backend — NVIDIA GPU only, so this number does not transfer to the M3 Max. https://github.com/robfiras/loco-mujoco/releases
- No published throughput benchmark exists for any of these humanoid models on Apple Silicon. Neither loco-mujoco (28 recent issues reviewed) nor GMR (31 recent issues reviewed) has a single macOS/Apple/arm64/M-series issue on file — meaning untested, not broken.
