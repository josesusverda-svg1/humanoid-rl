## Summary

MJX installs and runs correctly on macOS arm64, but CPU-only. There is no working GPU path for JAX on Apple Silicon: the JAX docs state plainly "JAX is not supported on Mac/OSX GPU; instead use the standard CPU installation commands," and Apple's jax-metal plugin is effectively abandoned (last release 0.1.1 on 2024-10-08, requiring jaxlib >=0.4.34, versus current jaxlib 0.11.0 of 2026-07-16). MJX-JAX is explicitly designed for "thousands or tens of thousands of scenes in parallel" on SIMD accelerators and the official docs warn it "can be 10x slower than MuJoCo" for a single scene, so running it batched on 14 CPU cores is the worst of both worlds. There is a live, unresolved performance regression (google-deepmind/mujoco#2957 -> jax-ml/jax#33761) where MJX on macOS runs up to ~2285x slower on jax>=0.7 due to the new XLA:CPU fusion emitters; still reproducing on jax 0.9.1 as of 2026-02-10, workaround is an XLA flag. The mujoco_warp / impl="warp" backend is CUDA-only for GPU (Warp "GPU support requires a CUDA-capable NVIDIA GPU"); it was enabled on macOS in April 2026 strictly as a CPU debugging path, not for throughput. For terrain, heightfield collision IS implemented in MJX-JAX (hfield vs sphere/capsule/box/mesh), but heightfield ray casting is NOT, which kills the standard raycast height-scan observation used in terrain locomotion. Blunt verdict: MJX is a dead end for training on this machine; use it only if you plan to rent an NVIDIA/TPU box, and use native multi-threaded C MuJoCo locally.

## Key facts

- mujoco-mjx latest is 3.11.0, released 2026-07-28, Apache-2.0, requires Python >=3.10, ships a single py3-none-any wheel — so it installs cleanly on macOS arm64 / Python 3.12. Deps: absl-py, etils[epath], jax, jaxlib, mujoco>=3.11.0.dev0, scipy, trimesh (source: PyPI JSON API, 2026-08-12).
- jaxlib 0.11.0 (2026-07-16) does publish cp312 macosx_11_0_arm64 wheels, so the install itself is not the problem — the backend is.
- JAX main-branch installation docs, verbatim: "JAX is not supported on Mac/OSX GPU; instead use the standard CPU installation commands." The support matrix lists Mac aarch64 CPU = yes, Apple GPU = "experimental", but that "experimental" link points straight at the not-supported sentence.
- jax-metal (Apple's Metal PJRT plugin) is dead: latest 0.1.1 released 2024-10-08, ~22 months stale, requires jaxlib >=0.4.34 while current jaxlib is 0.11.0. jax-ml/jax#34109 (opened 2025-12-26, still open) reports jax-metal failing on basic `jax.numpy.arange(10)` with "unknown attribute code: 22" StableHLO bytecode errors on jax 0.8.2 — i.e. it cannot deserialize modern JAX output at all.
- OPEN BUG, directly relevant: google-deepmind/mujoco#2957 "MJX on MacOS is >100x slower on jax>=0.7 than on jax<0.7" (opened 2025-11-26, still open). Measured on Darwin 24.6.0 arm64: mjx.kinematics on a 9-body/17-geom/8-site chain took 0.1784 ms/iter on jax 0.6.2 vs 407.88 ms/iter on jax 0.8.1 — a ~2285x regression, not merely 100x.
- Root cause and workaround, from jax-ml/jax#33761 (rdyro, 2025-12-08): "This seems to be caused by the new XLA:CPU fusion emitters, you can get the old behavior by disabling them: XLA_FLAGS=\"--xla_backend_extra_options=xla_cpu_disable_new_fusion_emitters=true\"". Confirmed still needed on jax 0.9.1 as of 2026-02-10 (hartikainen: "the problem still persists unless I explicitly disable the fusion emitters") and re-confirmed 2026-03-11. Current jax is 0.11.0; the issue remains open.
- MJX-Warp is NVIDIA-only for GPU. NVIDIA Warp docs: "Warp can run on x86-64 and ARMv8 CPUs on Windows and Linux, and on Apple Silicon (ARMv8) on macOS" but "GPU support requires a CUDA-capable NVIDIA GPU and driver (minimum GeForce GTX 9xx)." There is no Metal/MPS backend in Warp. The mujoco_warp repo tagline is literally "GPU-optimized version of the MuJoCo physics simulator, designed for NVIDIA hardware."
- impl="warp" WAS enabled on macOS — but only as a CPU debug path. MuJoCo commit 521d152 (2026-04-26), closing issue #2947: "This change modifies the Warp JAX FFI to register callbacks for both CUDA and CPU platforms... MJX's io.py is updated to allow Warp to use CPU devices if no CUDA GPU is available." The requester's stated motivation was "it would be really convenient to debug warp models locally," not training.
- TERRAIN — good news: heightfield collision IS implemented in MJX-JAX. mjx/_src/collision_driver.py registers (HFIELD, SPHERE) -> hfield_sphere, (HFIELD, CAPSULE) -> hfield_capsule, (HFIELD, BOX) -> hfield_convex, (HFIELD, MESH) -> hfield_convex. Docs: "PLANE, HFIELD, SPHERE, CAPSULE, BOX, MESH are fully implemented."
- TERRAIN — bad news: heightfield ray casting is NOT implemented in MJX-JAX. Feature-parity table, Ray casting row: MJX-Warp = "All, BVH for meshes, hfield, and flex"; MJX-JAX = "Slow for meshes, hfield and flex unimplemented." This removes the standard raycast height-scan / terrain-perception observation used in terrain locomotion policies.
- MJX-JAX unsupported geom pairs (docs footnote [3]): SDF geoms entirely; collisions between (SPHERE, BOX, MESH, HFIELD) and CYLINDER; collisions between (BOX, MESH, HFIELD) and ELLIPSOID. Practically: do not use cylinder or ellipsoid geoms anywhere on a humanoid you intend to run in MJX-JAX over heightfields.
- Other MJX-JAX gaps vs full MuJoCo: joint types limited to FREE/BALL/SLIDE/HINGE; transmissions JOINT/JOINTINPARENT/SITE/TENDON; solvers CG and NEWTON only (no PGS, no noslip); Jacobian DENSE only (no SPARSE); fluid model limited to the inertia model; flex not supported; sensors exclude PLUGIN; condim 1 not usable with ELLIPTIC cone.
- Mesh budget in MJX-JAX: "the convex decomposition of the mesh should have roughly 200 vertices or less for reasonable performance," and for convex-convex collisions "roughly fewer than 32 vertices" — because MJX-JAX uses a branchless Separating Axis Test rather than MuJoCo's MPR/GJK-EPA.
- MuJoCo Playground (the obvious ready-made MJX RL stack, RSS 2025 Outstanding Demo) documents a CUDA-12-only install path: `uv pip install -U "jax[cuda12]"` followed by a `jax.default_backend()` GPU verification step. No macOS or Apple Silicon install instructions are given.

## Reusable for this project

- The MJCF humanoid models themselves — mjx/test_data and MuJoCo Menagerie assets are plain XML and load identically into native MuJoCo. Zero lock-in cost to author models in the MJX-compatible subset (capsules/spheres/boxes, <200-vertex convex meshes, no cylinder/ellipsoid) so you retain the option to rent an NVIDIA box later without re-authoring.
- MJX's heightfield collision implementation as a reference for terrain: mjx/mujoco/mjx/_src/collision_convex.py (hfield_sphere, hfield_capsule, hfield_convex) and the hfield grid-bounds grouping logic in collision_driver.py, which shows how to bound the geom-vs-hfield pair set statically using hfield_nrow/hfield_ncol/hfield_size and geom_rbound.
- MuJoCo Playground's environment definitions, reward terms, terrain generators, domain-randomization code, and Brax-PPO wiring are pure Python on top of the mjx API. These are readable and portable as design references even if you run physics through native MuJoCo instead — the reward shaping and curriculum logic is the expensive part to get right, not the integration.
- Brax's PPO implementation (brax.training.agents.ppo) is a well-tested JAX PPO you can study or reuse; MJX-JAX is a successor to Brax's generalized pipeline, so the interfaces line up.
- The mjx feature-parity table is a useful authoring checklist regardless of backend — building the humanoid inside the MJX-supported subset costs nothing and preserves portability.
- The XLA_FLAGS fusion-emitter workaround is worth recording in your environment setup even if you use JAX only for the policy network on CPU: XLA_FLAGS=--xla_backend_extra_options=xla_cpu_disable_new_fusion_emitters=true.
- mujoco.testspeed is the right local benchmarking tool for the Phase 0 comparison — it is what DeepMind used to produce the 650K M3 Max figure, so your numbers will be directly comparable to the published ones.

## Blockers

- No GPU acceleration for JAX on this machine, period. JAX docs: "JAX is not supported on Mac/OSX GPU." The 30-core M3 Max GPU and Metal 4 are completely unused by MJX-JAX. Everything runs on the 14 CPU cores.
- jax-metal is abandoned — last release 2024-10-08 (v0.1.1), pinned to jaxlib >=0.4.34 while current jaxlib is 0.11.0. It is closed-source, so the JAX team cannot fix it; jax-ml/jax#34109 shows it failing on trivial ops. Do not plan around it.
- mujoco_warp / impl="warp" is disqualified for training: Warp's GPU backend requires a CUDA-capable NVIDIA GPU. On macOS Warp is CPU-only. The April 2026 macOS enablement was explicitly a debugging convenience for people whose real runs happen on Linux+CUDA.
- Open, unfixed ~100x-to-2285x MJX slowdown on macOS with jax>=0.7 caused by new XLA:CPU fusion emitters (mujoco#2957 / jax#33761). Requires setting XLA_FLAGS=--xla_backend_extra_options=xla_cpu_disable_new_fusion_emitters=true as a workaround, which is an undocumented, unsupported flag that may be removed. Still reproducing on jax 0.9.1 (2026-02-10); current jax is 0.11.0.
- Architectural mismatch: MJX-JAX is built for batches of thousands-to-tens-of-thousands of identical scenes on SIMD accelerators. On a 14-core CPU you cannot fill that batch. Official docs: single-scene MJX-JAX "can be 10x slower than MuJoCo." You would be paying MJX's vectorization overhead with none of its payoff.
- Heightfield ray casting unimplemented in MJX-JAX — blocks the standard terrain height-scan observation for the procedural-terrain phase of the project. You would have to fake it (e.g. sample the hfield array directly in Python/JAX outside the physics API) or drop raycast perception.
- No cylinder or ellipsoid collision against sphere/box/mesh/hfield in MJX-JAX. Constrains humanoid geom authoring: capsules/spheres/boxes/small meshes only.
- AMP/motion-imitation discriminator training adds a neural-net forward/backward pass per step on top of physics. On CPU-only JAX that competes with the physics for the same 14 cores — no separate accelerator to offload to.
- MuJoCo Playground, the most direct path to a working MJX PPO+locomotion pipeline, documents only a CUDA-12 install. You would be off the supported path from day one.
- No published MJX throughput number on Apple Silicon exists anywhere I could find — from DeepMind or the community. That absence is itself evidence: nobody benchmarks MJX on Macs because nobody trains on Macs with it.

## Performance evidence

- CORRECTION OF A WIDESPREAD MISREADING: the frequently-cited "650K steps/sec on Apple M3 Max" is NOT MJX. The MuJoCo docs (doc/mjx.rst, lines ~665-670) read: "We simulate this scene using CPU MuJoCo on an Apple M3 Max and a 64-core AMD 3995WX and time it using testspeed, using 2 x numcore threads. We time the MJX-JAX simulation on an Nvidia A100 GPU using a batch size of 8192 and an 8-chip v5 TPU machine using a batch size of 16384... The values for a single humanoid (leftmost datapoints) for the four timed architectures are 650K, 1.8M, 950K and 2.7M steps per second, respectively." So: 650K = native C MuJoCo on M3 Max CPU; 1.8M = native C MuJoCo on AMD 3995WX; 950K = MJX-JAX on A100; 2.7M = MJX-JAX on TPU v5. Several search engines and secondary sources misattribute the 650K to MJX. It is not.
- The useful corollary: native multi-threaded C MuJoCo on an M3 Max already does ~650K humanoid steps/sec via testspeed with 2x numcore threads. That is your realistic local baseline, and MJX-JAX on the same machine would be slower, not faster.
- MJX-Warp CUDA-graph benchmarks (docs, MJX-Warp section): Humanoid 3.35M SPS pure Warp / 2.96M SPS via JAX FFI (WARP) / 2.67M SPS (WARP_STAGED); Aloha Pot 2.45M / 2.33M / 1.96M SPS. All on NVIDIA hardware. Irrelevant to this machine.
- Docs, MJX-JAX Sharp Bits: "Simulating a single scene (1 instance of mjData), MJX-JAX can be 10x slower than MuJoCo, which has been carefully optimized for CPU. MJX-JAX works best when simulating thousands or tens of thousands of scenes in parallel."
- Docs also note MJX-JAX degrades faster than MuJoCo as contacts grow: "as we increase the number of humanoids (which increases the number of potential contacts in a scene), MJX-JAX throughput decreases more rapidly than MuJoCo." Contact-rich terrain locomotion is exactly the regime where MJX-JAX is weakest.
- macOS regression measurement (mujoco#2957, 2025-11-26, Darwin 24.6.0 arm64, mujoco 3.3.7): jax 0.6.2 -> 0.1784 ms/iter; jax 0.8.1 -> 407.88 ms/iter on the same jitted mjx.kinematics call. ~2285x.
- The only GPU-on-Mac JAX option with any life is the unofficial applejax (a fork of tillahoffmann/jax-mps, released 2026-03-11), a PJRT plugin over Metal Performance Shaders. Its own headline number is a 3x speedup over CPU on ResNet18/CIFAR-10 on an M4 MacBook Air (0.991 s/step MPS vs 3.041 s/step CPU). It pins jaxlib 0.9.x (current is 0.11.0) and documents hard limits: "No float64", "Linalg inside control flow — QR, SVD, eigh, eig crash inside scan/fori_loop/while_loop", "Zero-size arrays — MPS doesn't support empty tensors", "No jax.debug.print". MJX leans heavily on scan/while_loop (the constraint solver) and on float64 in places — this will not carry MJX. Treat as a non-option.
- MuJoCo Playground reports JIT compile times of 1-3 minutes on its tasks; on CPU-only XLA with the fusion-emitter workaround this will be worse, and every reward/terrain change re-triggers it.
