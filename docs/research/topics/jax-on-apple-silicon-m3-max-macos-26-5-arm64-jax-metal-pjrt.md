## Summary

Apple's jax-metal is dead. Its last PyPI release is 0.1.1 from 2024-10-08 — 22 months stale as of today. Apple's own documentation page has not even been updated to mention 0.1.1; its compatibility table stops at 0.1.0 and macOS "Sonoma 14.4+", which is two major OS releases behind the target machine's macOS 26.5. The JAX maintainers bulk-closed at least eleven Metal issues on 2026-01-20, and an Apple Developer Forums thread from February 2026 asking whether it is still supported has zero replies and no Apple response. The concrete failure is not subtle: jax-metal 0.1.1 ships a frozen StableHLO bytecode parser, so any modern jaxlib fails at compile time on something as trivial as jnp.arange(10) — reported on an M3 Max specifically in jax#34109 (2025-12-26). JAX's own installation docs state plainly that JAX is not supported on Mac GPU. Plain CPU JAX, by contrast, is fully and officially supported on Mac aarch64, with current cp312 arm64 wheels (jax/jaxlib 0.11.0, 2026-07-16) that install cleanly under uv on Python 3.12. The important caveat for this project is that JAX collapses all 14 CPU cores into a single device: only Eigen-backed ops are intra-op multithreaded, pmap on CPU requires a fake-device flag that has been an open unresolved request since 2022, and there is no way to pin work to the 10 P-cores. vmap over many envs is the only sound parallelism axis, and it will not approach GPU throughput.

## Key facts

- jax-metal latest release is 0.1.1, uploaded to PyPI 2024-10-08. Full release history: 0.0.2 (2023-06-06), 0.0.3 (2023-07-19), 0.0.4 (2023-09-20), 0.0.5 (2023-12-21), 0.0.6 (2024-03-12), 0.0.7 (2024-05-04), 0.1.0 (2024-06-11), 0.1.1 (2024-10-08). Nothing in 22 months.
- jax-metal 0.1.1 declares only jaxlib>=0.4.34 and jax>=0.4.34 — an open lower bound with no upper bound, which is a lie in practice: the plugin embeds a frozen StableHLO parser and breaks on any newer jaxlib.
- Apple's official page developer.apple.com/metal/jax/ has a compatibility table that stops at jax-metal 0.1.0 / macOS 'Sonoma 14.4+' / jaxlib >=v0.4.26. It does not mention 0.1.1 at all. Apple has not updated its own documentation since before its own last release.
- Target machine runs macOS 26.5. Apple's newest documented jax-metal OS is Sonoma 14.4 — two full major OS generations behind (14 -> 15 -> 26). There is zero documented support for this machine.
- jax#34109 'jax-metal fails to run on recent macOS' (opened 2025-12-26, CLOSED) reproduces on an Apple M3 Max — the exact chip class of the target — with macOS 15.6.1, jax/jaxlib 0.8.2, jax-metal 0.1.1, Python 3.13. jnp.arange(10) fails with 'error: unknown attribute code: 22 ... bytecode version 6 produced by StableHLO_v1.13.0'.
- Same root cause reported 9 months earlier in jax#26968 (opened 2025-03-06, closed): jax 0.5.2 on Apple M3, error 'unknown attribute code: 22 ... StableHLO_v0.19.0'. Install succeeds and the Metal device is even detected, but no computation can execute. This is a hard, total failure, not a partial one.
- Bulk closure event: at least 11 Metal issues in jax-ml/jax were closed on a single day, 2026-01-20 — #20296 (memory leak at jit boundary), #20750 (lax.scan SEGFAULT on M1), #16416 (complex math), #7163, #16287 (failed to legalize mhlo.custom_call), #16321 (mhlo.cholesky), #16435 (crash creating float64 arrays), #17490 (mhlo.triangular_solve), #19841 (element type f32 vs si32 assertion), #19886, #20112 (reduction canonicalization error).
- Apple Developer Forums thread 815139 (Feb 2026), 'Is Jax for Apple Silicon is still supported': user reports 'in DEC 2025 the Jax maintainers have closed all issues citing No active development on Jax-metal and the project seems dead.' The thread has ZERO replies and no official Apple response six months later.
- Official JAX installation docs state: 'JAX is not supported on Mac/OSX GPU; instead use the standard CPU installation commands.' The supported-platforms table lists Mac aarch64 as CPU = yes, Apple GPU = no.
- jax-metal has no public source repository — it is a closed binary PJRT plugin from Apple. Unlike an abandoned OSS project, it cannot be forked, patched, or rebuilt against a current StableHLO. Abandonment is therefore terminal, not recoverable.
- jax and jaxlib 0.11.0 released 2026-07-16 with requires_python >=3.12. Confirmed macOS arm64 wheels: jaxlib-0.11.0-cp312-cp312-macosx_11_0_arm64.whl (plus cp313, cp314, cp314t). Python 3.12 via uv is directly supported.
- JAX CPU threading reality: JAX abstracts all CPU cores into a SINGLE device. Only some ops are intra-op multithreaded — Eigen-backed ops such as matmul are; others (e.g. FFT) are not. Controlled via XLA_FLAGS (--xla_cpu_multi_thread_eigen, intra_op_parallelism_threads), which must be set before JAX imports or they are ignored.
- pmap on CPU is not a real parallelism path. It requires XLA_FLAGS=--xla_force_host_platform_device_count=N to fabricate N logical devices. jax#10404 'Control the parallelism on CPU' (opened 2022-04-21) is STILL OPEN after 4+ years and states JAX 'doesn't provide any API to control (in a coarse-grain manner) the parallelism on multiple CPU cores', explicitly asking to make xla_force_host_platform_device_count performant for pmap. It has not been done.
- There is no mechanism in JAX or XLA:CPU to pin work to the 10 performance cores. macOS QoS scheduling will place threads on the 4 efficiency cores too, so effective throughput is below a naive 10-core estimate and is not controllable from JAX.
- Live alternative jax-mps (github.com/tillahoffmann/jax-mps, Apache-2.0) is a PJRT plugin routing StableHLO to MLX. Created 2026-01-21, last push 2026-08-04, 209 stars, 22 open issues. Latest 0.10.10 (2026-07-18), wheel jax_mps-0.10.10-py3-none-macosx_14_0_arm64.whl — macOS 14+, py3-none so Python-version-agnostic (PJRT C API), requires_python >=3.11. Python 3.12 is fine.
- jax-mps HARD-PINS jax<0.11,>=0.10.0 and jaxlib<0.11,>=0.10.0 because it matches StableHLO bytecode to a specific jaxlib. Using it means staying on jax 0.10.x, not the current 0.11.0. Its version number tracks the jaxlib it targets (0.9.x -> jaxlib 0.9, 0.10.x -> jaxlib 0.10). It has the same structural fragility that killed jax-metal, just with an active maintainer keeping pace.
- jax-mps started on MPSGraph and migrated to MLX after hitting MPSGraph bugs — per jax discussion #34648 (2026-01-27), maintainer Jake VanderPlas (@jakevdp) called the StableHLO approach 'a really sound one', and the author confirmed 'the project now uses the MLX backend'. This is community work, not a Google or Apple product.
- jax-mps limitations directly relevant to PPO: single-device only, no multi-device/collective/sharding ops (so no pmap at all), no float64, no int4/uint4/float8/float4. Test suite reports 95.2% passing with those exclusions.
- jax-mps has open performance bugs that hit exactly the PPO rollout pattern: issue #215 (2026-07-17) 'lax.scan with stacked outputs: per-iteration cost grows linearly with T (quadratic total)' and issue #196 (2026-07-05) 'MCMC is slow: random.split inside fori_loop is slow'. A PPO rollout is a scan with stacked outputs and per-step PRNG splits.
- jax#35063 (2026-02-13, closed as NOT PLANNED): 'MPS backend: gather unsupported pattern with vmap over Flax nn.scan model init' — vmap over a Flax model init using nn.scan crashes MPS with 'gather: unsupported gather pattern', though raw jax.lax.scan works.
- mujoco-mjx 3.11.0 (2026-07-28, requires_python >=3.10) depends on jax and jaxlib UNPINNED. That is convenient: MJX will not fight a downgrade to jax 0.10.x if you want to test jax-mps.
- MJX docs claim 'MJX-JAX runs on: Nvidia and AMD GPUs, Apple Silicon, and Google Cloud TPUs' — but on Apple Silicon this now means the CPU backend only, since jax-metal is dead. Read that line as aspirational, not as a working GPU path.
- MJX docs warn: 'Simulating a single scene (1 instance of mjData), MJX-JAX can be 10x slower than MuJoCo, which has been carefully optimized for CPU. MJX-JAX works best when simulating thousands or tens of thousands of scenes in parallel.' Without a GPU, the regime where MJX wins is unreachable on this machine.
- mujoco#2813 'An MJX-style JAX FFI for CPU-based MuJoCo' (opened 2025-08-23, still OPEN, assigned to mmossg) notes MJX 'speed scales poorly for more complex scenes with many objects and contacts' and 'Jax/MJX compilation is often slow, which makes debugging, visualization, and testing quite tedious'. A contact-rich humanoid on terrain is exactly the poorly-scaling case.

## Reusable for this project

- mujoco-mjx 3.11.0 (2026-07-28) — unpinned jax/jaxlib dependency, so it composes with either jax 0.11.0 (CPU) or a jax 0.10.x + jax-mps configuration. Useful even if you end up CPU-only, because MJX model/data structures are shared with native MuJoCo.
- Native MuJoCo C via the `mujoco` Python package as the physics backend instead of MJX, with process-level vectorization (one env per P-core) rather than JAX vmap. The M3 Max 650K steps/s single-humanoid figure makes this the highest-confidence fast path on this exact hardware, and it sidesteps every JAX-Metal and XLA:CPU threading problem in this report.
- google-deepmind/mujoco_playground — GPU-accelerated robot learning and sim-to-real library built on MJX; its humanoid locomotion environments, terrain generation, and PPO configs are directly on-topic for procedural terrain and waypoint courses, and are worth reading even if you re-target the backend.
- Brax — its PPO implementation and MJX integration (Brax joined with the MuJoCo authors on MJX) is reusable as a reference PPO for JAX, and the paper 'Learning Velocity-based Humanoid Locomotion: Massively Parallel Learning with Brax and MJX' (arXiv 2407.05148) is a direct precedent for the humanoid-walking target.
- jax-mps 0.10.10 as a Phase 0 EXPERIMENT ONLY — install it, run one MJX step function under JAX_PLATFORMS=mps, and measure. It is the only living Metal path for JAX. Do not build the project on it; treat it as a benchmark data point that either justifies or rules out a GPU lane.
- XLA_FLAGS tuning knobs for the Phase 0 hardware-check script: --xla_cpu_multi_thread_eigen and intra_op_parallelism_threads, set BEFORE importing jax. Use these to empirically measure whether your MJX step actually scales across cores on this machine rather than assuming it does.
- mujoco#2813 (open) is worth subscribing to — an official MJX-style JAX FFI over CPU MuJoCo would be close to the ideal backend for this project on this hardware: JAX-authored env logic, native-C physics speed, no Metal dependency.

## Blockers

- jax-metal is disqualified outright: last release 2024-10-08, no public source to fork, Apple docs never updated past 0.1.0/Sonoma 14.4, and it hard-fails at compile time on modern jaxlib due to a frozen StableHLO bytecode parser. Confirmed broken on an M3 Max in jax#34109 (2025-12-26).
- Using jax-metal would force pinning the entire stack to jax/jaxlib ~0.4.34-0.4.35 (October 2024) — which would in turn drag mujoco-mjx, Flax, and Optax back ~22 months. Even then it is unverified on macOS 26.5, and the previously-closed issue list shows lax.scan segfaults (#20750) and mhlo legalization failures on the very primitives an MJX physics step emits.
- No CUDA path exists on this machine, and JAX's official docs state Mac GPU is not supported. Therefore the realistic JAX plan is CPU-only, which forfeits the massively-parallel-envs regime that makes MJX+PPO fast in the first place.
- JAX exposes all 14 cores as ONE device. pmap over the 10 P-cores is not a real option — it needs XLA_FLAGS=--xla_force_host_platform_device_count and jax#10404, the open request to make that performant, has been unresolved since 2022-04-21. Any plan that assumes 'pmap across 10 P-cores' should be dropped.
- No P-core pinning is possible from JAX/XLA. macOS will schedule XLA threads onto the 4 efficiency cores as well, so measured scaling will fall short of a 10-core projection in a way you cannot fix from Python.
- Intra-op CPU threading only helps Eigen-backed ops (matmul). MJX physics is dominated by small irregular kernels, scatter/gather, and control flow, not big GEMMs — so the multithreading that does exist covers the wrong part of this workload. Batch via vmap to create wide ops, or the cores sit idle.
- MJX's own documentation says single-scene MJX-JAX is ~10x slower than native MuJoCo C, and that it only pays off at thousands-to-tens-of-thousands of parallel scenes. On CPU-only hardware you land in the worst quadrant: MJX's overhead without MJX's payoff.
- jax-mps is a viable GPU escape hatch but carries real risk: it is one maintainer, 7 months old, single-device only (no pmap), no float64, and hard-pinned to jax 0.10.x — so adopting it freezes your JAX version and reintroduces the exact version-skew coupling that killed jax-metal.
- jax-mps has open bugs on the precise PPO access pattern: quadratic cost for lax.scan with stacked outputs (#215) and slow random.split inside fori_loop (#196). A rollout buffer built as a scan with per-step PRNG splits may be pathologically slow until those land.
- Reported jax-mps speedup is only ~3.7x over the JAX CPU backend (ResNet18/CIFAR-10, M4 MacBook Air) — and that is on a dense-conv workload that suits MLX. A contact-heavy MJX step is far less favorable, so do not budget 3.7x for this project.
- jax-mps requires macOS 14+ arm64 (wheel tag macosx_14_0_arm64) and is single-device with no collectives — meaning no sharding strategy is available if a single 96 GB device is not enough.
- Version-lock conflict to plan around: jax 0.11.0 requires Python >=3.12 (fine), but jax-mps caps at jax<0.11. You cannot run current JAX and jax-mps at the same time; pick one lane before pinning dependencies in Phase 0.

## Performance evidence

- MuJoCo native C on CPU, Apple M3 Max: ~650K steps/second for a single humanoid. Source: MuJoCo MJX docs benchmark figure (mujoco.readthedocs.io/en/stable/mjx.html). This is the SAME CHIP as the target machine and is the single most important number here.
- For comparison in the same MJX benchmark: Nvidia A100 running MJX-JAX at batch 8192 reaches ~950K steps/s on the humanoid; TPU v5 at batch 16384 reaches ~2.7M steps/s; AMD 3995WX native MuJoCo CPU reaches ~1.8M steps/s. The M3 Max's native-C 650K is within ~1.5x of an A100 running MJX — a strong argument that the CPU MuJoCo path is competitive on this specific machine.
- MJX docs, explicit: 'Simulating a single scene (1 instance of mjData), MJX-JAX can be 10x slower than MuJoCo, which has been carefully optimized for CPU.'
- jax-mps (MLX backend) vs JAX CPU backend, ResNet18 on CIFAR-10, M4 MacBook Air: 0.928 s/step vs 3.437 s/step = ~3.7x speedup. Source: jax-mps README. Victor Glazer's write-up (2026-04-12) independently characterizes it as 'on the order of ~4x' over the CPU backend.
- No published throughput benchmark exists for MJX or any PPO/RL workload running on jax-mps or on jax-metal on Apple Silicon. Every Apple-Silicon RL number you may want has to be measured yourself in Phase 0 — treat any projection as unvalidated.
- No credible jax-metal performance numbers exist at all for current software, because the plugin does not execute on any modern jaxlib (jax#26968, jax#34109). Any speedup figure found online predates October 2024 and is untestable today.
