## Summary

MuJoCo 3.11.0 (released 2026-07-28, Apache-2.0) is actively developed — commits landed on the repo today, 2026-08-12, and 12 releases shipped in the last 12 months. It ships a prebuilt cp312 macosx_11_0_arm64 wheel; I installed and benchmarked it on this exact M3 Max / macOS 26.5 machine with uv + Python 3.12 and everything worked with zero compilation and zero configuration. The decisive finding for architecture: the Python bindings release the GIL for essentially the entire C API — the generic Def<> template in python/mujoco/functions.h applies py::call_guard<py::gil_scoped_release> to all 213 bound functions, and mj_step has its own explicit release plus an nstep argument that runs N steps without reacquiring. I measured this directly: pure mj_step across Python threads scales 9.06x on 10 threads (532k steps/s aggregate for the 27-DoF humanoid), so use threads, not processes, for parallel envs. In a realistic RL loop with Python-side obs/reward the GIL glue caps scaling at ~6.3x on 8 threads (52.8k env-steps/s at frame_skip=5), which is still far better than paying process IPC. Heightfields and fully headless offscreen rendering with mp4 export both work on macOS via CGL with no MUJOCO_GL setting and no mjpython, but MJX and MuJoCo Warp are not viable on this hardware and procedural terrain has a real render-staleness gotcha.

## Key facts

- VERSION: mujoco 3.11.0 is latest on PyPI, uploaded 2026-07-28T01:22:20; changelog dates it July 27, 2026. requires_python >=3.10, classifiers cover 3.10-3.14.
- ARM64 WHEEL: mujoco-3.11.0-cp312-cp312-macosx_11_0_arm64.whl (17.5 MB) exists. I installed it on this M3 Max / macOS 26.5 (25F71) with uv + CPython 3.12.13 and mujoco.mj_versionString() returned 3.11.0 on arm64. No compilation, no Rosetta.
- MACOS x86_64 WHEELS DROPPED in 3.11.0: 3.10.0 shipped macosx_10_16_x86_64 wheels; 3.11.0 ships only macosx_11_0_arm64 for Mac. Apple Silicon is now the ONLY supported Mac architecture — this is a signal that arm64 is the first-class Mac target, not a tolerated one.
- GIL RELEASED FOR ALL PHYSICS (decisive): python/mujoco/functions.h Def<> template applies `::pybind11::call_guard<::pybind11::gil_scoped_release>()` to every bound function. functions.cc has 213 `Def<traits::...>` bindings and ZERO uses of the `DefWithGil` opt-out. mj_step additionally has its own explicit `py::call_guard<py::gil_scoped_release>()` (functions.cc line 126). Present unchanged in tags 3.3.0, 3.4.0 and 3.11.0 — long-standing, not new.
- mj_step SIGNATURE: mj_step(m, d, nstep=1) loops nstep times inside C with the GIL released, so N physics steps cost one binding crossing. Docs: 'the first one does so without acquiring the GIL in between subsequent physics steps.'
- OFFICIAL DOC CONFIRMATION: 'The bindings releases the Python Global Interpreter Lock (GIL) before calling the underlying MuJoCo function... the GIL is only released for the duration of the MuJoCo C function itself, and not during the execution of any other Python code.'
- THREADS NOT PROCESSES: measured pure mj_step across Python threads (own MjModel/MjData each) on this machine — 1 thread 54.7k steps/s, 2 threads 1.87x, 4 threads 3.76x, 8 threads 7.19x, 10 threads 9.06x (532k steps/s), 12 threads 9.76x (574k), 14 threads regresses to 9.25x. Sweet spot = 10-12 threads matching the 10 performance cores.
- mujoco.rollout IS OPEN-LOOP ONLY — signature is rollout(model, data, initial_state, control=..., nstep=...) taking a PRECOMPUTED control array. There is no policy/action callback hook. It CANNOT drive PPO rollouts that require per-step policy inference. It is for MPC/sampling planners, system ID, and finite differencing.
- rollout internals (python/mujoco/rollout.cc): uses a native C++ ThreadPool, wraps the work in `py::gil_scoped_release no_gil`, and the module is declared `PYBIND11_MODULE(_rollout, pymodule, pybind11::mod_gil_not_used())`. Measured throughput: 49k steps/s single-threaded, 358k at 8 threads, 430k at 14 threads — scales monotonically since no Python runs per step.
- mju_threadpool(d, nthread) added in 3.10.0 (commit b935d415, 2026-06-22): creates a thread pool on an MjData and parallelizes collision detection and constraint solving ACROSS ISLANDS. BREAKING: header mjthread.h and the old engine threading API were REMOVED in the same release.
- mju_threadpool IS USELESS FOR A SINGLE HUMANOID — I measured it: baseline 50.4k steps/s vs 54.4k/53.7k/53.2k/53.9k steps/s at 2/4/8/10 pool threads, all within run-to-run noise, with nisland=1 in every case. One connected humanoid is one island, so island-level parallelism has nothing to split. Parallelize across envs instead.
- SINGLE-CORE HUMANOID THROUGHPUT (measured, official model/humanoid/humanoid.xml, nv=27 nq=28 nu=21, dt=0.005, settled onto floor with 9-13 active contacts): ~55,000-60,000 steps/s, i.e. roughly 280-300x realtime on one M3 Max performance core.
- INTEGRATOR COST (measured, same model): Euler 58.7k steps/s, implicitfast 55.3k (-6%), implicit 35.1k (-40%), RK4 18.2k (-69%). implicitfast is nearly free relative to Euler and is the right default for humanoid stability.
- SOLVER COST (measured): Newton 55.9k steps/s, CG 57.1k, PGS 37.0k. Newton and CG are comparable; PGS is ~35% slower. Newton is the recommended default.
- FRICTION CONE (measured): pyramidal 56.6k steps/s vs elliptic 60.2k steps/s — elliptic measured slightly FASTER, contradicting the common assumption that elliptic is the expensive option. Difference is ~6% and near run-to-run variance, so treat as 'elliptic costs nothing here', not as 'elliptic is faster'.
- SOLVER ITERATION BUDGET BARELY MATTERS: iterations=100/50/20/10/5 gave 55.7k/56.3k/55.0k/54.7k/56.3k steps/s. Newton early-terminates long before the cap, and 3.11.0 added a duality-gap certificate letting CG and Newton 'terminate with zero iterations' when the warmstarted solution already meets tolerance. Do not bother tuning this down for speed.
- REALISTIC RL LOOP THROUGHPUT (measured, frame_skip=5 = 200Hz physics / 40Hz control, plus a 376-dim numpy obs concat and reward computation in Python per control step): 1 thread 8,379 env-steps/s; peak 52,840 env-steps/s at 8 threads (6.31x); then DEGRADES — 10 threads 5.91x, 12 threads 5.72x, 14 threads 4.97x. The Python obs/reward glue holds the GIL and becomes the bottleneck past 8 threads.
- HEIGHTFIELDS WORK: hfield asset with nrow/ncol/size compiles and collides. m.hfield_data is a flat float32 array (normalized elevations) writable from Python at runtime. I regenerated a 128x128 hfield 10 times in 0.9 ms total. Physics picks up new terrain IMMEDIATELY with no upload call — verified by stepping a sphere onto regenerated terrain.
- RENDER STALENESS GOTCHA (verified experimentally): after writing new m.hfield_data, renders show the OLD terrain. Mean absolute pixel difference between two radically different terrains was exactly 0.000 until I called mujoco.mjr_uploadHField(m, renderer._mjr_context, hfield_id), after which the diff became 14.67. Physics and visuals silently disagree until you upload. Note renderer._mjr_context is a PRIVATE attribute.
- macOS RENDERING IS CGL ONLY: python/mujoco/rendering/classic/gl_context.py hard-codes valid MUJOCO_GL values per platform. Linux gets ('glx','egl','osmesa'); Darwin gets only ('cgl'). EGL and OSMesa are Linux-exclusive branches — on macOS they raise RuntimeError. Any tutorial telling you to set MUJOCO_GL=egl or osmesa is Linux-only advice and WILL fail here.
- HEADLESS OFFSCREEN RENDERING WORKS OUT OF THE BOX: with MUJOCO_GL unset, mujoco.Renderer resolved to mujoco.cgl.GLContext and rendered 640x480 RGB at 232 fps (4.30 ms/frame) in a plain non-GUI process — no window, no display, no mjpython. Depth rendering and segmentation rendering both worked.
- OFFSCREEN RENDERING WORKS FROM A NON-MAIN THREAD — I rendered a 320x240 frame from a spawned threading.Thread successfully. The macOS main-thread restriction applies only to the interactive passive viewer, not to offscreen CGL contexts.
- mjpython IS NOT NEEDED for this project. Docs: 'On MacOS, launch_passive requires that the user script is executed via a special mjpython launcher.' That constraint is scoped to the interactive viewer only; headless training and video export use plain python.
- END-TO-END MP4 EXPORT VERIFIED: rendered 120 frames at 640x480 with physics stepping and wrote a valid 685 KB mp4 in 1.06 s (112.8 fps including physics), using imageio + imageio-ffmpeg whose bundled binary is native arm64 (ffmpeg-macos-aarch64-v7.1).
- FREE-THREADED PYTHON SUPPORT: 3.11.0 changelog item 37 (commit a07ae6f8) — 'The bindings now support free threading (PEP 703) for Python 3.14.' 3.11.0 ships cp314t wheels including macosx_11_0_arm64. This is a future escape hatch from the ~6.3x GIL ceiling, but 3.12 is the pinned target so it is not available today.
- 3.11.0 ENGINE FEATURES RELEVANT TO THIS PROJECT: geom/surfacevel (commit 4787c809) models conveyor belts/treadmills with static geoms and no DoF — potentially useful for treadmill-style gait training. geom/adhesion (a264d0bc) for sticky contacts. implicitfast now applies gyroscopic derivatives to free bodies (f0fa3d82), so spinning free bodies no longer gain energy.
- VERY FEW macOS BUGS: GitHub search for open issues with 'macOS' in the title returns only 2 total, and 'Apple Silicon' and 'arm64' return 0 open issues each. The CPU engine on Mac is not a source of active breakage.

## Reusable for this project

- mujoco.mj_step(m, d, nstep=frame_skip) — do the whole frame-skip inside one GIL-free C call instead of a Python loop. Free throughput, one-line change.
- Python threading.Thread-based vectorized env wrapper — since all 213 bindings release the GIL, a thread pool with one MjModel/MjData per env gives 6-8x on this machine with zero IPC, zero pickling, and shared numpy buffers. This replaces SubprocVecEnv entirely; do NOT write a multiprocessing env layer.
- mujoco.Renderer + mujoco.cgl.GLContext for headless video export — works unconfigured on macOS, 232 fps at 640x480, usable from a worker thread. Covers the Phase 3 'Videos mode' requirement with no extra dependencies beyond imageio-ffmpeg.
- Renderer.enable_depth_rendering() / enable_segmentation_rendering() — ready-made depth and segmentation observation channels if the policy ever needs vision (subject to the macOS depth-precision caveat).
- m.hfield_data as a directly writable float32 numpy array — the whole procedural terrain curriculum (Phase 4) can be driven by writing a numpy heightmap into this array in-place, at ~0.09 ms per 128x128 regeneration, with no model recompilation.
- mujoco.mjr_uploadHField(m, ctx, hfield_id) — the required companion call to keep rendered terrain in sync with physics terrain when regenerating heightfields.
- mujoco.mj_getState / mj_setState with mjtState.mjSTATE_FULLPHYSICS — clean full-state save/restore primitives for episode resets, waypoint-course checkpointing, and deterministic replay.
- mujoco.rollout.Rollout(nthread=N) as a context manager with persistent_pool — NOT for PPO, but directly reusable later if you add sampling-based MPC, gait system identification, or finite-difference gradients, at ~430k steps/s.
- model/humanoid/humanoid.xml from the MuJoCo repo (nv=27, nq=28, nu=21) — sits exactly in the 25-35 DoF target band and is a ready baseline/sanity model for Phase 1-2 before the anthropometric model exists.
- geom/surfacevel (new in 3.11.0) — models a treadmill with a static geom and no extra DoF, a cheap way to train sustained gait in place without translating the world.
- mujoco.mju_threadpool(d, nthread) — not useful for one humanoid, but worth reusing if a scene ever holds many independent bodies (multi-agent courses), where island parallelism does apply.

## Blockers

- MJX IS NOT USABLE ON THIS MACHINE. Open issue #2957 (filed 2025-11-26, still open, no assignee or PR): 'MJX on MacOS is >100x slower on jax>=0.7 than on jax<0.7' — 0.178 ms/iter on JAX 0.6.2 degrading to 407.88 ms on JAX 0.8.1, reported on Darwin arm64. Plan on CPU MuJoCo only; do not budget for MJX acceleration.
- MuJoCo Warp (MJWarp) IS DISQUALIFIED — CUDA-ONLY. It was launched in MuJoCo 3.5 (2026-02-13) and is explicitly 'optimized for NVIDIA GPUs', developed jointly with NVIDIA under the Linux Foundation Newton project. There is no Metal backend. Bluntly: the entire GPU-accelerated MuJoCo story (MJX-on-GPU and MJWarp) is unavailable to you, and the 30-core M3 Max GPU will contribute nothing to physics. All physics runs on the 10 CPU performance cores.
- GIL CEILING ON REALISTIC ENV LOOPS: threading scales only ~6.3x (peaking at 8 threads) once per-step Python obs/reward code is included, and actively DEGRADES beyond 8 threads. To approach the ~9-10x pure-physics ceiling you must push per-step work out of Python — batch obs assembly across envs, keep reward math in vectorized numpy over all envs at once, or move the env step into C. Budget for ~50k env-steps/s, not ~570k.
- mujoco.rollout CANNOT BE USED FOR PPO. It only accepts a precomputed open-loop control array with no policy callback, so it cannot query a network between steps. Do not plan the PPO data-collection path around it; it is only useful if you later add an MPC/planner or system-ID component.
- PROCEDURAL TERRAIN RENDER STALENESS: changing m.hfield_data updates physics but NOT visuals until mjr_uploadHField is called against the renderer's OpenGL context. Verified: zero pixel change without it. Worse, the context is only reachable via the private renderer._mjr_context attribute, which is not a stable public API and could break across releases. Your terrain-curriculum videos will silently show the wrong terrain if you miss this.
- macOS OPENGL IS DEPRECATED AND LEGACY. MuJoCo's CGL context requests CGLOGLPVersion_Legacy (OpenGL 2.1) because Apple deprecated OpenGL in 10.14 and never shipped a modern core profile. Concrete consequence I hit: 'WARNING: ARB_clip_control unavailable while mjDEPTH_ZEROFAR requested, depth accuracy will be limited'. If you need accurate depth images as policy input, that precision loss is real. Apple could remove the OpenGL framework in a future macOS, which would break all MuJoCo rendering on Mac.
- MY THROUGHPUT NUMBERS ARE FOR THE STOCK 27-DoF humanoid.xml, which uses cheap primitive geoms (17 bodies, 20 geoms, capsules/spheres). A 'realistic human-proportioned humanoid' with mesh collision geometry, more contact pairs, hands/feet detail, or higher geom count will be materially slower — plan for 2-5x lower throughput and re-benchmark once the actual model exists. Do not size the training budget off these figures.
- Heightfield collision cost was measured with a single sphere on a 128x128 hfield (263k steps/s), NOT with a humanoid's many foot contacts on rough terrain. Heightfield contact cost scales with the number of active contacts and terrain resolution; re-measure before committing to a terrain resolution.
- BREAKING CHANGE IF ANY DEPENDENCY IS OLD: 3.10.0 removed the mjthread.h header and the entire old engine threading API, and renamed mjData.efc_diagApprox to efc_diagA; mj_fullM changed signature. Third-party packages pinned to older MuJoCo internals (some RL/mocap libraries) may not yet be compatible with 3.10/3.11.

## Performance evidence

- MEASURED BY ME on the target machine (Apple M3 Max, Mac15,11, 10P+4E cores, 96 GB, macOS 26.5 build 25F71, arm64), 2026-08-12, mujoco 3.11.0 + CPython 3.12.13, official model/humanoid/humanoid.xml (nv=27, nq=28, nu=21), dt=0.005 s, humanoid settled onto floor with 9-13 active contacts. All figures below are from those runs.
- Single core, default config (Euler + Newton + pyramidal): 58,774 steps/s = 294x realtime.
- Integrator sweep single-core: Euler 58,651 | implicitfast 55,295 | implicit 35,125 | RK4 18,160 steps/s.
- Solver sweep single-core: Newton 55,931 | CG 57,074 | PGS 36,987 steps/s.
- Friction cone single-core: pyramidal 56,578 | elliptic 60,238 steps/s (elliptic marginally faster, within ~6%).
- Newton iteration cap sweep single-core: iter=100 -> 55,668 | 50 -> 56,325 | 20 -> 55,049 | 10 -> 54,710 | 5 -> 56,303 steps/s (essentially flat).
- Pure mj_step across N Python threads (each with its own MjModel/MjData), total aggregate steps/s: 1t=54,658 (1.00x) | 2t=109,712 (1.87x) | 4t=221,222 (3.76x) | 6t=330,683 (5.63x) | 8t=422,432 (7.19x) | 10t=532,286 (9.06x) | 12t=573,687 (9.76x) | 14t=543,593 (9.25x, regression). Near-linear scaling to 10 threads is direct proof the GIL is released.
- Realistic RL env loop (ctrl write + mj_step(nstep=5) + 376-dim numpy obs concat + reward, per control step), total env-steps/s: 1t=8,379 (1.00x) | 2t=16,157 (1.93x) | 4t=31,212 (3.72x) | 6t=40,708 (4.86x) | 8t=52,840 (6.31x, PEAK) | 10t=49,556 (5.91x) | 12t=47,948 (5.72x) | 14t=41,642 (4.97x). Peak equals ~264,000 physics steps/s.
- mujoco.rollout (native C++ threadpool, nbatch=256, nstep=200, no Python per step): single 49,331 | 2t=95,504 | 4t=189,386 | 8t=358,177 | 10t=394,010 | 12t=414,171 | 14t=430,055 steps/s. Monotonic — no GIL contention.
- mju_threadpool on one humanoid (nisland=1): baseline 50,429 vs 54,448 / 53,730 / 53,242 / 53,862 steps/s at 2/4/8/10 threads — no meaningful gain.
- Heightfield: sphere on a 128x128 procedural hfield ran at 263,951 steps/s; regenerating the 16,384-cell hfield 10 times took 0.9 ms total.
- Offscreen CGL rendering: 640x480 RGB at 232.3 fps (4.30 ms/frame). Full render+encode pipeline: 120 frames at 640x480 with physics in 1.06 s = 112.8 fps, producing a 685 KB mp4.
- CONTEXT / SANITY CHECK on third-party claims: a search result asserted 'MJX achieves 650,000 steps/second on Apple M3 Max for a single humanoid model.' I could not verify this against any primary source and I do not believe it is meaningful for this decision — MJX on macOS is the subject of open bug #2957 reporting >100x slowdowns on modern JAX. Treat that number as unsubstantiated. My own measured CPU aggregate of ~530-574k steps/s across 10-12 threads is the number to plan against.
