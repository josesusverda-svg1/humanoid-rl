## Summary

MLX is healthy, current, and fully supported on this exact machine — I installed it and benchmarked it during this research. mlx 0.32.0 (2026-07-07, MIT) installs cleanly under Python 3.12 via uv on macOS 26.5 arm64, and the repo had commits today (2026-08-13), so maintenance is not a concern. Every op PPO needs is present (Adam/AdamW/Muon, optim.clip_grad_norm, LR schedules, Linear/LayerNorm/RMSNorm/Tanh, nn.value_and_grad, mx.random.categorical/normal, mx.compile with state capture) with one gap: there is no torch.distributions equivalent, so Gaussian log-prob/entropy must be hand-written (~15 lines; rlx already has it). On my own measurements MLX beats PyTorch MPS modestly on the PPO update step (3.34 ms vs 4.26 ms at batch 4096; 46.7 ms vs 62.4 ms at 65536), beats it ~2x on rollout forward latency, and beats it ~12x on the numpy→GPU path that MuJoCo actually needs (25 us vs 302 us per 1 MB) — but "zero-copy unified memory" is a myth for CPU numpy input: I verified pointers differ and mutations are invisible even with mx.asarray. The real hazard is a ~235-340 us Metal sync-latency floor per mx.eval that is independent of batch size, which caps sequential rollout stepping at ~3-4k policy queries/sec and must be amortized with many parallel envs. The bigger risk is ecosystem, not framework: rlx is the only serious MLX RL library (260 stars, v1.0.0, good CleanRL-style PPO) and I could not import it on this machine at all due to a broken envpool dependency, and nothing in the MLX world implements AMP, mocap retargeting, or vectorized MuJoCo.

## Key facts

- mlx 0.32.0 released 2026-07-07 (GitHub Releases and PyPI agree). License MIT. requires-python >=3.10. Ships cp312 macosx_13_0_arm64 and macosx_14_0_arm64 wheels.
- VERIFIED LOCALLY: `uv pip install mlx` into a Python 3.12.13 venv on this machine installed mlx==0.32.0 plus a separate mlx-metal==0.32.0 backend package. The Metal backend split into its own wheel is new — pin both.
- VERIFIED LOCALLY: mx.device_info() reports {'device_name': 'Apple M3 Max', 'architecture': 'applegpu_g15s', 'memory_size': 103079215104, 'max_recommended_working_set_size': 83494174720, 'max_buffer_length': 62620631040}. ~83 GB usable GPU working set — memory is a non-issue for tiny MLPs.
- VERIFIED LOCALLY: every PPO-required op exists — optim.Adam, optim.AdamW, optim.Muon, optim.clip_grad_norm, cosine_decay/linear_schedule/join_schedules, nn.Linear/LayerNorm/RMSNorm/Tanh/ELU, nn.value_and_grad, mx.random.categorical/normal/multivariate_normal/gumbel/truncated_normal/bernoulli.
- GAP CONFIRMED: MLX has NO distributions module. `[m for m in dir(mx) if 'dist' in m]` returns only ['distributed']. Gaussian log-prob, entropy and tanh-squash Jacobian correction must be hand-written. This is ~15 lines and rlx/utils/distributions.py already implements Categorical, Gaussian and SquashedNormal.
- mx.compile supports training-step compilation with state capture: @partial(mx.compile, inputs=[model.state, optimizer.state], outputs=[...]). shapeless=True avoids recompilation on varying batch. MEASURED: gives only ~20-25% on our PPO step (matmul-bound, little to fuse), not the 5x the docs' GELU example advertises. On the CPU device mx.compile actively HURT (4096: 29.3ms eager vs 34.0ms compiled).
- MEASURED on M3 Max, PPO minibatch step (obs 60, act 21, two 2x512 MLPs, full clipped-surrogate + value loss + Adam + clip_grad_norm), ms/step: batch 4096 -> MLX GPU 4.31, MLX GPU+compile 3.34, PyTorch MPS 4.26, MLX CPU 29.3. batch 16384 -> 14.31 / 11.79 / 13.59 / 105.1. batch 65536 -> 55.23 / 46.71 / 62.42 / 427.4. MLX+compile is ~20-25% faster than PyTorch MPS across the range.
- MEASURED many-small-matmuls (N chained (B,H)@(H,H), one sync), ms: B=4096 H=512 N=32 -> MLX GPU 9.59 vs Torch MPS 9.23 (tie). B=16384 H=512 N=32 -> 36.0 vs 34.1 (tie). B=65536 H=256 N=32 -> MLX 35.1 vs Torch MPS 64.7 (MLX 1.8x faster on skinny/wide). Verdict: MLX and PyTorch MPS are at parity on small-matmul throughput; MLX wins on wide-batch/narrow-hidden shapes, which is exactly the RL shape.
- NUMPY INTEROP IS *NOT* ZERO-COPY INTO MLX. Verified by pointer comparison: mx.array(np) gave numpy_ptr=70002c000 vs mlx_ptr=10c6f0000, same=False, mutation_visible=False. mx.asarray(np) gave the same result (different pointer, mutation invisible). The docs' zero-copy claim covers DLPack imports (e.g. PyTorch MPS tensors), NOT plain numpy CPU arrays.
- MEASURED numpy -> MLX copy cost: 25.7 us for 0.98 MB, 60.4 us for 3.93 MB, 254.8 us for 15.73 MB (~40-60 GB/s host memcpy). mx.asarray is only ~5-10% faster than mx.array. In absolute terms this is cheap — 26 us to push a 4096x60 observation batch.
- MLX -> numpy IS genuinely zero-copy: np.array(mlx_arr, copy=False) measured at 0.4-0.7 us CONSTANT regardless of size (4096 through 65536 rows). Getting actions back out to MuJoCo is free.
- DECISIVE ADVANTAGE vs PyTorch MPS on the MuJoCo path: getting a 0.98 MB numpy array onto the compute device costs 25.7 us in MLX vs 302.4 us in PyTorch MPS (torch.from_numpy().to('mps')); at 15.73 MB it is 254.8 us vs 587.5 us. MLX is ~12x better at the small end. This is the exact CPU-MuJoCo -> GPU-network hop our architecture requires every rollout step.
- CRITICAL LATENCY FLOOR: MLX Metal sync costs ~235-340 us per mx.eval REGARDLESS of work size. Measured mx.eval(a+1) on a scalar: 235.3 us on GPU vs 14.2 us on CPU. Policy forward+eval measured 259.8 us at n_envs=1, 285.1 us at 64, 342.0 us at 512, 774.9 us at 4096 — essentially flat until the work dominates.
- The floor is submission latency, not throughput: queueing forwards before a single eval gave 340.9 us for 1, 104.0 us each for 4, 51.7 us each for 16, 32.1 us each for 64. But RL rollouts CANNOT queue — you need the action realized on host to step MuJoCo. Budget ~300 us of dead time per rollout iteration.
- PyTorch MPS has the SAME problem, worse: rollout forward+.cpu() measured 486.1 us at n=1, 578.9 us at n=64, 566.5 us at n=512 — roughly 2x MLX's latency. Neither GPU backend is good at low-latency sequential inference.
- MLX CPU device is dramatically better for small-batch inference: 37.7 us at n=1 and 158.3 us at n=64, versus 259.8/285.1 us on GPU. It crosses over around n=256-512 and is terrible at n=4096 (6.4 ms). Unified memory + per-op `stream=`/`mx.set_default_device` means a hybrid (rollout inference on the CPU stream, PPO update on the GPU stream) needs NO data movement — this is a real, structural MLX advantage PyTorch MPS cannot match.
- rlx (github.com/noahfarr/rlx) is the ONLY serious MLX RL library: 260 stars, 19 forks, MIT, v1.0.0 tagged 'Production/Stable' on 2026-06-30, last commit 2026-07-01, 0 open issues, created 2024-01-22.
- rlx PPO quality is good, CleanRL-style single-file: uses mx.compile on update_step with inputs/outputs=[network.state, optimizer.state], nn.value_and_grad, optim.clip_grad_norm (max_grad_norm 0.5), advantage normalization, value-loss clipping, entropy bonus, minibatching over update_epochs. Has both discrete and continuous PPO. rlx/utils/distributions.py provides Categorical, Gaussian and SquashedNormal with tanh Jacobian correction and log-std clamping to [-5, 2].
- rlx is NOT on PyPI — https://pypi.org/pypi/rlx/json returns HTTP 404. Install is git clone + uv sync only.
- rlx's advertised 'over a million environment steps per second on Apple silicon' refers to its MLX-NATIVE GPU environments (classic control + MinAtar, written branchless in MLX). It is not a MuJoCo number and does not transfer to our workload.
- rlx's GAE (rlx/utils/utils.py compute_generalized_advantage_estimate) is a Python for-loop over reversed timesteps building an O(T)-deep lazy MLX graph before one mx.stack. Fine for short horizons, but for long rollouts compute GAE in numpy on CPU instead.
- mlx-cuda exists on PyPI under Apple's org (owners awni, mlx-dev), latest 0.30.0 released 2025-11-20, manylinux_2_35_x86_64 wheel. So MLX code is not permanently Apple-locked — but the CUDA package lags the Metal one by two minor versions.
- Every other MLX RL project is a toy: teilomillet/textpolicy (14 stars, LLM text RL), kzahedi/snake-ppo (0 stars), sungjinnam/art-of-rl-mlx (0 stars), adriandelser/PongRL (0 stars, last push 2024-06-21), jiemingyou/mlx-reinforcement-learning (0 stars, last push 2023-12-18 — DEAD).
- Reproducibility caveat: MLX issue #3568 reports mx.random.normal with seeded keys produces bit-different results across chip generations (M1 Max vs M3 Ultra vs M5). Seeded runs are not portable across Macs.
- Historical benchmark claims in circulation are stale and contradictory — MLX issue #243 (opened 2023-12-21) measured PyTorch MPS 10-11x FASTER than MLX on ResNet training, while the widely-cited Towards Data Science 'How Fast Is MLX' benchmark (published 2024-02-02) measured MLX ~2x faster on Linear layers. Both predate MLX 0.1. Ignore them; my measurements above were taken on the target machine with mlx 0.32.0 and torch 2.13.0.

## Reusable for this project

- rlx/utils/distributions.py — Categorical, Gaussian and SquashedNormal in MLX with log_prob, entropy, sample, mode, tanh Jacobian correction and log-std clamping. Directly fills MLX's missing distributions module. Vendor this file; do not depend on the package.
- rlx/algorithms/ppo.py — a complete, working, mx.compile'd PPO with advantage normalization, value-loss clipping, entropy bonus, grad-norm clipping and minibatched multi-epoch updates. Verified importable standalone (it does not pull envpool). This is the single highest-value artifact to crib from; expect to rewrite the env interface.
- rlx/utils/utils.py compute_generalized_advantage_estimate — correct GAE reference, though I recommend reimplementing it in numpy to avoid building an O(T)-deep lazy graph.
- mlx.optimizers.clip_grad_norm — drop-in, no need to write gradient clipping.
- mlx.optimizers schedules (cosine_decay, linear_schedule, join_schedules) — covers PPO LR annealing out of the box.
- mx.compile(fn, inputs=[model.state, opt.state], outputs=[...], shapeless=True) — the documented training-step compilation pattern; worth ~20-25% on the update.
- MLX streams / mx.set_default_device — lets you put rollout inference on the CPU device (37-158 us at small batch) and the PPO update on the GPU device (3.3 ms at 4096) with ZERO data movement thanks to unified memory. This hybrid is the single most valuable MLX-specific architectural lever for this project and has no PyTorch MPS equivalent.
- np.array(mlx_arr, copy=False) — free 0.4 us zero-copy handoff of actions back to MuJoCo.
- My benchmark scripts, ready to fold into Phase 0 task #1: /private/tmp/claude-502/-Users-BrickLayer-Desktop-HumonoidAI/24c51158-3311-4d49-a1c8-8e6bff1681b1/scratchpad/bench_mlx.py (MLX PPO step + interop + rollout latency), bench2.py (zero-copy pointer proof + dispatch-overhead floor + CPU/GPU crossover), bench3.py (many-small-matmuls MLX vs Torch), bench_torch.py (PyTorch MPS equivalents). The venv at .../scratchpad/mlxtest has mlx 0.32.0, mlx-metal 0.32.0, torch 2.13.0, numpy 2.5.2.

## Blockers

- No torch.distributions equivalent. Gaussian log-prob, entropy, tanh-squash correction, and any AMP discriminator loss must be hand-written. Small (~15 lines) but it is real work and a real source of subtle bugs. Mitigation: vendor rlx/utils/distributions.py.
- ~235-340 us Metal sync-latency floor per mx.eval, independent of batch size. Sequential rollout stepping (unavoidable with CPU MuJoCo) is capped at ~3-4k policy queries/sec on the GPU device. You MUST run many parallel envs (>=256, ideally 512-1024) to amortize this, or run rollout inference on the MLX CPU device (37-158 us) and only the PPO update on GPU. PyTorch MPS has the same floor, ~2x worse.
- 'Zero-copy unified memory' does not apply to numpy input. I verified mx.array and mx.asarray both copy from a plain numpy array (different pointers, mutations invisible). Every MuJoCo observation batch costs a host memcpy. It is cheap (26 us per MB) but do not architect assuming it is free. Only the MLX->numpy direction is truly zero-copy.
- rlx CANNOT BE IMPORTED ON THIS MACHINE AS-IS — verified failure. `import rlx` -> rlx/environments/__init__.py imports EnvPool -> rlx/environments/envpool.py does a module-level `import envpool` -> envpool/entry.py imports envpool.procgen -> procgen_envpool.so fails dlopen on 'Library not loaded: /opt/homebrew/opt/qt@5/lib/QtGui.framework/Versions/5/QtGui' (not installed; /opt/homebrew/opt/qt@5 does not exist). Workarounds: `brew install qt@5` (Qt5 is EOL), or vendor rlx's files directly — I confirmed `rlx.algorithms.ppo` imports fine standalone.
- rlx 1.0.0's design assumes MLX-native GPU-resident vectorized environments. Its only bridge to external simulators is the EnvPool adapter, which is the exact thing that is broken. There is no MuJoCo integration path in rlx; you would be writing the env interface yourself.
- Total ecosystem gap for this project: no AMP/adversarial motion prior implementation exists in MLX, no mocap retargeting, no BVH/AMASS loaders, no vectorized MuJoCo binding, no RL logging/eval/checkpointing infrastructure, no terrain-curriculum tooling. MLX gives you the array math and optimizers; everything above that is from scratch. PyTorch has rsl_rl, skrl, Stable-Baselines3 and multiple public AMP implementations to crib from.
- mx.compile delivers only ~20-25% on this workload (matmul-bound, little elementwise to fuse), and is a net NEGATIVE on the CPU device. Do not budget for large compile wins. Also note compiled functions must be pure — no Python side effects, and shape changes trigger recompilation unless shapeless=True.
- Seeded runs are not bit-reproducible across different Apple chips (MLX issue #3568). Fine for a single-machine project; a problem if results must be reproduced elsewhere.
- Historical macOS 26 Tahoe hazard: MLX issue #3337 (opened 2026-03-30, now closed) — MLX 0.31.1 failed to compile Metal kernels against Metal Toolchain 32023 (metal::vec namespace migration, missing <metal_types> include), silently falling back to CPU (35 tok/s -> 17 tok/s). Fixed by 0.32.0 and I confirmed the prebuilt 0.32.0 wheel works here, but it is a reminder to avoid building MLX from source on this OS.
