## Summary

dm_control is the clear winner and should be the backbone of this project. It is actively maintained (1.0.44 released 2026-07-28), Apache-2.0, and ships almost every piece the project needs: a genuinely human-proportioned CMU humanoid with 56 actuators including ankles and toes, a complete mocap-tracking task with multi-term imitation rewards, curated walking clip subsets, and procedural heightfield terrain that regenerates per episode. Critically, the CMU mocap data is distributed pre-converted as a ~477 MB HDF5 file from Google Cloud Storage with SHA256 verification, so no ASF/AMC conversion pipeline needs to be written. Gymnasium 1.3.0 is healthy and its vector wrappers plus the v5 `xml_file` parameter are reusable, but Humanoid-v5 itself is disqualified as the target body: it has no ankle joints at all and its feet are 0.075 m spheres, which makes a human-like heel-strike/toe-off gait physically impossible. mujoco_menagerie is very actively maintained but contains only robot humanoids (H1, G1, Talos, Apollo, etc.), none human-proportioned, and its advertised A+/A/B/C quality grades are not actually populated yet. HumanoidBench is effectively frozen — last real code commit 2025-05-20, only LICENSE edits since — and its hard `==` pins (gymnasium 0.29.1, mujoco 3.1.6, brax 0.9.4) make it unusable as a dependency, though its reward and task source is worth reading. Separately and bluntly: GPU-accelerated batched simulation via MJX is not available on this machine, because jax-metal has been dead since 2024-10-08 while JAX has moved to 0.11.0; plan on CPU MuJoCo across the 10 performance cores.

## Key facts

- dm_control 1.0.44 released 2026-07-28, Apache-2.0, python_requires >=3.9, depends on mujoco>=3.11.0 (source: PyPI JSON API).
- mujoco 3.11.0 released 2026-07-28 ships a native cp312 macosx_11_0_arm64 wheel (verified in the PyPI file list: mujoco-3.11.0-cp312-cp312-macosx_11_0_arm64.whl), alongside cp310-cp314. MuJoCo is a CPU C library with no CUDA dependency, so the core simulator is fully native on M3 Max.
- REUSABLE / HIGHEST VALUE: the CMU mocap dataset is distributed PRE-CONVERTED as HDF5 and auto-downloaded by dm_control/locomotion/mocap/cmu_mocap_data.py from https://storage.googleapis.com/dm_control/cmu_2020_dfe3e9e0.h5 (~477 MB, 2020 default; the 2019 version cmu_2019_08756c01.h5 is ~488 MB). It is SHA256-verified and cached in the package dir or ~/.dm_control/. This removes the entire ASF/AMC->MJCF conversion pipeline from the project's scope.
- REUSABLE: dm_control's CMU humanoid (dm_control/locomotion/walkers/cmu_humanoid.py) is human-proportioned with 56 joints/actuators derived from the CMU mocap skeleton, and crucially INCLUDES ankles (lfootrx, lfootrz, rfootrx, rfootrz) AND toes (ltoesrx, rtoesrx). Assets: humanoid_CMU_V2019.xml (21,172 bytes) and humanoid_CMU_V2020.xml (21,958 bytes). Variants: CMUHumanoid, CMUHumanoidPositionControlled, CMUHumanoidPositionControlledV2020 (adds a nose geom for head-orientation tracking); position-controlled variants scale ctrlrange to [-1, 1].
- REUSABLE: CMUHumanoidObservables exposes ready-made proprioceptive observables: joints_pos, joints_vel, actuator_activation, body_height, end_effectors_pos, appendages_pos, world_zaxis, plus head_height, sensors_torque, egocentric_camera, body_camera. This is a validated observation set for imitation — no need to invent one.
- REUSABLE: dm_control/locomotion/tasks/reference_pose/ is a complete mocap-tracking task package — tracking.py (42,506 bytes), rewards.py (7,092 bytes), cmu_subsets.py (30,022 bytes), utils.py, types.py, mocap_playback.py, plus tests (tracking_test.py 11,259 bytes).
- REUSABLE (imitation rewards): rewards.py defines termination_reward_fn (key: 'termination', computed as 1 - termination_error/termination_error_threshold), multi_term_pose_reward_fn (keys: 'center_of_mass', 'body_quaternions', 'joints_velocity', 'appendages', combined with exponential decay), and comic_reward_fn (50/50 blend of termination and pose terms). These are the CoMic (ICML 2020) reward terms and map almost directly onto a DeepMimic/AMP-style tracking objective.
- REUSABLE (clip selection): cmu_subsets.py defines curated named subsets — GET_UP (~7 clips), WALK_TINY (~35 clips, ~2 min of walking), RUN_JUMP_TINY (~50 clips, ~2 min walk/run/jump), LOCOMOTION_SMALL (~240 clips, ~40 min varied locomotion), and ALL (~1000+ clips, ~3.5 h). WALK_TINY is the natural Phase 3 starting point; LOCOMOTION_SMALL is the natural scale-up.
- REUSABLE (procedural terrain, directly serves Phase 4): dm_control/locomotion/arenas/bowl.py generates a genuine MuJoCo heightfield. Terrain = bowl_shape * smooth_bumps where bumps = random_state.uniform(_TERRAIN_SMOOTHNESS, 1, (bump_res, bump_res)) then ndimage.zoom-smoothed. Parameters: 201x201 hfield resolution, 6x6 m extent, 0.5 m height range, _TERRAIN_SMOOTHNESS = 0.5 (0 = maximally bumpy, 1 = flat), bump scale 0.2 m. It REGENERATES PER EPISODE via initialize_episode when self._regenerate is set — exactly the pattern needed for a difficulty curriculum (tune _TERRAIN_SMOOTHNESS as the curriculum knob).
- REUSABLE (waypoint courses, serves Phase 5): dm_control/locomotion/arenas/ also ships corridors.py (16,100 bytes) and mazes.py (18,348 bytes), plus floors.py (3,731 bytes), covering.py, and labmaze_textures.py. corridors.py gives corridor-style navigation arenas; mazes.py builds on labmaze (a declared dm_control dependency).
- dm_control also ships dm_control/suite/utils/parse_amc.py (6,868 bytes) for parsing raw CMU AMC files directly, and dm_control/suite/humanoid_CMU.py (7,048 bytes) + humanoid_CMU.xml (18,061 bytes) as a simpler Suite-level CMU humanoid — a lighter-weight alternative to the full locomotion walker.
- DISQUALIFIER FOR Humanoid-v5 AS THE TARGET BODY: I read Gymnasium's own asset gymnasium/envs/mujoco/assets/humanoid.xml directly. It defines 17 actuators (abdomen_y/z/x, hip_x/z/y x2, knee x2, shoulder1/2 x2, elbow x2) and has NO ankle joints whatsoever. The feet are single spheres: <geom name="right_foot" pos="0 0 0.1" size="0.075" type="sphere"/>. With no ankle DoF and a spherical contact patch there is no plantarflexion, no heel-strike, no toe-off — a human-like gait is not representable in this model. Note this differs from MuJoCo's own model/humanoid/humanoid.xml, which DOES have ankle_y/ankle_x per leg and 21 actuators.
- Humanoid-v5 specifics (Gymnasium docs): 348-dim observation (45 joint pos/vel, 130 mass/inertia, 78 COM velocities, 17 actuator forces, 78 contact forces), 17-dim action in [-0.4, 0.4], 1000-step episodes, terminates outside torso height [1.0, 2.0]. Reward = 5.0 healthy + 1.25*x-velocity - 0.1*||a||^2 - 5e-7*contact. v5 restored the contact cost that was broken in v4, dropped zero-valued worldbody observations, added tendon length/velocity, and — the genuinely useful part — added an `xml_file` parameter so a custom MJCF can be swapped in while keeping the Gymnasium env scaffolding.
- Gymnasium 1.3.0 released 2026-04-22, MIT, python_requires >=3.10. The `mujoco` extra pulls mujoco>=2.1.5, imageio>=2.14.1, packaging>=23.0 — loose lower bounds, so it composes fine with mujoco 3.11.0.
- Gymnasium vectorization: AsyncVectorEnv(env_fns, shared_memory=True, copy=True, context=None, daemon=True, worker=None, observation_mode='same', autoreset_mode=...). shared_memory defaults to True and context defaults to the platform default. SyncVectorEnv runs in-process. Docs state vector envs 'can provide a linear speed-up in the steps taken per second' but explicitly decline to rank sync vs async: relative performance 'depends on many factors, notably the complexity of the environment itself and the hardware used'. No published Apple Silicon numbers.
- mujoco_menagerie is very actively maintained (last push 2026-08-09, 3814 stars, 527 forks) but contains ONLY robot humanoids, none human-proportioned: unitree_h1, unitree_g1, pal_talos, booster_t1, apptronik_apollo, berkeley_humanoid, fourier_n1, robotis_op3, pndbotics_adam_lite, toddlerbot_2xc, toddlerbot_2xm, plus the biped agility_cassie.
- mujoco_menagerie QUALITY GRADES ARE NOT ACTUALLY POPULATED. The README defines the scale (A+ = 'values are the product of proper system identification', A = 'realistic, but have not been properly identified', B = 'stable, but some values are unrealistic', C = 'conditionally stable') but states grading will only be applied 'once a proper system identification toolbox is created'. Do not cite menagerie model quality as verified — the table is empty.
- Menagerie models ship MJX-specific variants: unitree_g1 contains g1.xml (23,446 B), g1_with_hands.xml (35,285 B), g1_mjx.xml (27,445 B), scene.xml, scene_with_hands.xml, scene_mjx.xml. The _mjx variants are simplified for accelerator constraints — not useful here given MJX is off the table, but they document which collision geometry was too expensive.
- HumanoidBench robots and tasks: Unitree H1 in four variants (h1 locomotion-only, h1hand with dexterous hands, h1simplehand low-dim, h1touch tactile), Unitree G1 with three-finger hands, and Digit. 27 tasks total — 12 locomotion (walk, run, reach, crawl, hurdle, maze, stand, sit x2, balance x2, stair, slide) and 15 manipulation (push, cabinet, door, truck, cube, bookshelf x2, basketball, window, spoon, kitchen, package, powerlift, pole, insert x2, highbar). No terrain generation or procedural terrain in the repo.
- HumanoidBench baselines included: TD-MPC2, DreamerV3, SAC, and PPO via stable-baselines3 2.3.2, plus hierarchical training on pre-trained low-level reaching policies. It supports both classic CPU MuJoCo and an MJX/JAX path.
- HumanoidBench dependency wall — every pin is a hard `==`: gymnasium==0.29.1, mujoco==3.1.6, mujoco-mjx==3.1.6, dm_control==1.0.20, torch==2.3.1, brax==0.9.4, gymnax==0.0.8, imageio==2.34.2, opencv-python==4.10.0.84, rich==13.7.1, tqdm==4.66.4, ipdb==0.13.13, natsort==8.4.0. python_requires is '>3.7' but the README instructs conda create python=3.11.
- HumanoidBench install risk detail: mujoco 3.1.6 DOES have a cp312 macosx_11_0_arm64 wheel (uploaded 2024-06-03), so that pin alone is survivable on Python 3.12. The real breakage is brax==0.9.4 (uploaded 2024-01-04), whose requires_dist includes the deprecated `gym` package and `pytinyrenderer`; `gym` does not install cleanly on Python 3.12. gymnasium==0.29.1 is also pre-1.0 and uses the older step/reset API, so it cannot coexist with Gymnasium 1.3.0 in one environment.
- MJX ON APPLE SILICON IS A DEAD END, despite the docs. mujoco.readthedocs.io/en/stable/mjx.html lists 'Nvidia and AMD GPUs, Apple Silicon, and Google Cloud TPUs' — but 'Apple Silicon' there means the JAX CPU backend, not GPU. The docs also warn: 'Simulating a single scene, MJX-JAX can be 10x slower than MuJoCo', that accelerators 'exhibit poor performance for branching code' in collision detection, and that MJX throughput 'decreases more rapidly than MuJoCo' as contact count grows. A contact-rich humanoid on a heightfield is precisely the worst case.
- jax-metal IS ABANDONED: latest release 0.1.1 on 2024-10-08 — roughly 22 months stale as of 2026-08-12 — and it requires jax>=0.4.34/jaxlib>=0.4.34. Current JAX is 0.11.0 (released 2026-07-16, python_requires >=3.12). The version gap is unbridgeable. The community replacement jax-mps is a PJRT plugin lowering StableHLO to MPSGraph; it is self-described as 'in a very early stage' with incomplete op coverage, delivers only ~3x over CPU (ResNet18/CIFAR-10 on an M4 MacBook Air), and its own maintainer calls MPSGraph 'extremely buggy, poorly documented and its performance is very unpredictable' and has moved to an MLX backend.
- dm_control rendering on macOS: three backends exist (EGL headless+accelerated, GLFW windowed+accelerated, OSMesa software), selected via MUJOCO_GL with default preference GLFW -> EGL -> OSMesa. EGL is effectively Linux/NVIDIA. On macOS, GLFW is the working path but is windowed. Open issue #464 'Headless rendering on Mac?' (created 2024-04-12) reports Physics.render() hanging on headless macOS. Open issue #377 (2023-01-27) reports that importing dm_control.viewer on macOS kills matplotlib windows because of a global glfw.init() in glfw_renderer.py.
- dm_control macOS install note from the README: if using a Homebrew Python, set DYLD_LIBRARY_PATH=$(brew --prefix)/lib:$DYLD_LIBRARY_PATH before running. Open issue #511 (2025-03-12) reports install failure on Python 3.13 (Bazel 8 WORKSPACE deprecation), with Python 3.10 or conda-forge as the workaround — a reason to stay on Python 3.12 as planned rather than moving to 3.13.

## Reusable for this project

- BODY MODEL: dm_control/locomotion/walkers/assets/humanoid_CMU_V2020.xml (21,958 B) with cmu_humanoid.CMUHumanoidPositionControlledV2020 — human-proportioned, 56 actuators, ankles + toes, position-controlled with ctrlrange normalised to [-1, 1]. This is the single most important reuse and directly replaces Humanoid-v5 as the Phase 2/3 body.
- MOCAP DATA (no pipeline needed): dm_control/locomotion/mocap/cmu_mocap_data.py auto-downloads the pre-converted cmu_2020_dfe3e9e0.h5 (~477 MB) with SHA256 verification and caching. Load via HDF5TrajectoryLoader in dm_control/locomotion/mocap/loader.py; clips are Trajectory objects from mocap/trajectory.py. Deletes the entire ASF/AMC conversion task from the backlog.
- IMITATION REWARDS (Phase 3): dm_control/locomotion/tasks/reference_pose/rewards.py — comic_reward_fn, multi_term_pose_reward_fn (terms: center_of_mass, body_quaternions, joints_velocity, appendages) and termination_reward_fn. Use these as the tracking reward directly, or as the 'task reward' half of an AMP objective with a learned style discriminator supplying the other half.
- TRACKING TASK SCAFFOLD: dm_control/locomotion/tasks/reference_pose/tracking.py (42,506 B) implements clip selection, reference-pose phase indexing, early termination on tracking error, and initialisation from reference states (reference state initialisation is the standard DeepMimic trick). Worth reading closely before writing any of it.
- CLIP CURRICULUM: cmu_subsets.WALK_TINY (~35 clips, ~2 min pure walking) as the Phase 3 starting set, escalating to LOCOMOTION_SMALL (~240 clips, ~40 min). GET_UP (~7 clips) is useful if fall-recovery is ever wanted.
- OBSERVATION SET: CMUHumanoidObservables — joints_pos, joints_vel, actuator_activation, body_height, end_effectors_pos, appendages_pos, world_zaxis. A validated proprioceptive spec; copy it rather than inventing an observation vector.
- PROCEDURAL TERRAIN (Phase 4): dm_control/locomotion/arenas/bowl.py — a working MuJoCo hfield generator (201x201, 6x6 m, 0.5 m height range) using uniform noise in [_TERRAIN_SMOOTHNESS, 1] smoothed by ndimage.zoom, regenerated per episode in initialize_episode. Lift this function wholesale and expose _TERRAIN_SMOOTHNESS (default 0.5) as the curriculum difficulty knob.
- WAYPOINT COURSES (Phase 5): dm_control/locomotion/arenas/corridors.py (16,100 B) and mazes.py (18,348 B) for navigation layouts, floors.py for flat baselines, plus the labmaze dependency already pulled in by dm_control.
- ENV SCAFFOLD: Gymnasium 1.3.0's MujocoEnv with the v5 `xml_file` parameter — keep the Gymnasium API surface, PPO tooling compatibility, and wrapper ecosystem while pointing it at the CMU humanoid MJCF instead of the ankle-less default model.
- VECTORIZATION: gymnasium.vector.SyncVectorEnv and AsyncVectorEnv(shared_memory=True, context=..., daemon=...) for fanning out across the 10 performance cores. Benchmark both; do not assume async.
- RAW AMC FALLBACK: dm_control/suite/utils/parse_amc.py (6,868 B) if a specific CMU clip outside the packaged HDF5 is ever needed.
- REFERENCE READING ONLY (do not install): humanoid-bench's task and reward definitions for hurdle, stair, slide, maze, balance and pole — useful prior art for terrain and navigation reward shaping, and its PPO/stable-baselines3 3.2.x config as a hyperparameter starting point. Vendor ideas, not the package.
- MJCF REFERENCE: mujoco_menagerie unitree_g1/g1.xml and unitree_h1 for actuator modelling, armature/damping conventions and sensor setup — good MJCF craftsmanship to imitate even though the morphologies are wrong for this project.

## Blockers

- MJX / GPU-batched simulation is unavailable on M3 Max. jax-metal's last release was 2024-10-08 (v0.1.1, pinned to jax>=0.4.34) while current JAX is 0.11.0 (2026-07-16). Any plan that assumes thousands of parallel MJX envs on the 30-core GPU will fail. Budget for CPU MuJoCo parallelised across the 10 performance cores instead.
- Gymnasium's Humanoid-v5 model cannot express a human-like gait: zero ankle DoF and 0.075 m sphere feet (verified in gymnasium/envs/mujoco/assets/humanoid.xml). Using it as the Phase 2 'placeholder humanoid' risks baking in a body that must be thrown away in Phase 3. Prefer the dm_control CMU humanoid, or at minimum MuJoCo's own model/humanoid/humanoid.xml which has ankle_y/ankle_x.
- HumanoidBench cannot be installed alongside a modern stack. Its hard pins (gymnasium==0.29.1 pre-1.0 API, brax==0.9.4 which depends on the dead `gym` package, dm_control==1.0.20, torch==2.3.1) conflict irreconcilably with Gymnasium 1.3.0 / dm_control 1.0.44 / mujoco 3.11.0. Treat it as source code to read and vendor selectively, not as a dependency. If it must be run, isolate it in a separate Python 3.11 uv venv.
- Headless rendering on macOS is unreliable — dm_control issue #464 (open since 2024-04-12) reports Physics.render() hanging headless on Mac; EGL is Linux/NVIDIA-only. For the Videos mode in Phase 3, plan on MUJOCO_GL=glfw with a real window, or OSMesa software rendering as a slow fallback. Do not assume offscreen GPU rendering works.
- AsyncVectorEnv on macOS + Python 3.12 uses the spawn start method, so every env_fn and everything it closes over must be picklable, and per-worker startup pays a full interpreter + MuJoCo model reload. There is a known Gymnasium issue (#1161) about pickle errors for ctypes in MujocoRenderer under async vec envs — so render-enabled sub-envs in particular are a hazard. Benchmark SyncVectorEnv against AsyncVectorEnv before assuming async wins; Gymnasium's own docs decline to say which is faster.
- h5py is an OPTIONAL extra of dm_control (extra == 'hdf5'), but the CMU mocap HDF5TrajectoryLoader in dm_control/locomotion/mocap/loader.py needs it. Installing plain `dm_control` will import fine and then fail at mocap load time. Install dm_control[hdf5].
- The ~477 MB CMU mocap HDF5 is downloaded at first use from storage.googleapis.com and cached to the package dir or ~/.dm_control/. This is a network dependency and a non-trivial download; pre-fetch and pin it into the repo's setup step rather than discovering it mid-training. It also means the mocap data is not vendored in the pip package.
- dm_control fails to install on Python 3.13 (issue #511, Bazel 8 WORKSPACE deprecation). Staying on Python 3.12 is correct, but this constrains any future interpreter upgrade.
- mujoco_menagerie contains no human-proportioned humanoid — every humanoid is a real robot (H1, G1, Talos, Apollo, Berkeley, Fourier N1, OP3, Booster T1, Adam-lite, ToddlerBot). If the project genuinely wants 'realistic human proportions', the menagerie is the wrong source for the body model; it is useful only if the goal shifts to a robot morphology.
- mujoco_menagerie's A+/A/B/C quality grades are declared in the README but not yet assigned to any model ('will be applied to each model once a proper system identification toolbox is created'). Any claim about a specific menagerie model's physical fidelity is currently unverifiable from the repo itself.
- HumanoidBench has an SPDX NOASSERTION (non-standard) license at the repo level, and mujoco_menagerie models each carry their own per-model license. If any of this is vendored, the licenses must be checked individually rather than assumed permissive. dm_control (Apache-2.0) and Gymnasium (MIT) are clean.

## Performance evidence

- MuJoCo docs (mjx.html, stable as of 2026-08): 'Simulating a single scene, MJX-JAX can be 10x slower than MuJoCo.' This is the key number arguing for plain CPU MuJoCo on this machine.
- MuJoCo docs (mjx.html): accelerators 'exhibit poor performance for branching code' in collision detection, and MJX-JAX throughput 'decreases more rapidly than MuJoCo' as contact count increases; convex meshes should have 'roughly 200 vertices or less'. A humanoid with feet on a 201x201 heightfield is contact-rich, i.e. MJX's worst case.
- jax-mps community benchmark cited in jax-ml/jax discussion #34648: approximately 3x speedup over CPU training ResNet18 on CIFAR-10 on an M4 MacBook Air. This is the only concrete Apple-Silicon JAX GPU number I found, it is for a CNN rather than physics, and the plugin is early-stage.
- Gymnasium docs (api/vector/): vector envs 'can provide a linear speed-up in the steps taken per second through sampling multiple sub-environments at the same time', but the docs explicitly state that relative Sync vs Async performance 'depends on many factors, notably the complexity of the environment itself and the hardware used'. No numbers given.
- GAP — I found NO published MuJoCo steps/second benchmarks for a humanoid on M3 Max or any Apple Silicon part from a primary source. Phase 0 of this project should measure it directly (mj_step throughput for humanoid_CMU on flat ground vs. on a 201x201 hfield, 1 thread vs 10) rather than relying on any figure from the literature.
