## Summary

LocoMuJoCo is alive, MIT-licensed, and I verified it installs and runs correctly on this exact machine (macOS 26.5, arm64, Python 3.12) — I installed v1.1.0 from git and benchmarked it. It is the best-matched candidate I found for the project's stated goal: it ships a realistic human-proportioned humanoid (SkeletonTorque / SkeletonMuscle, 27 actuators, 65-dim obs), auto-downloads 19 named mocap motions per humanoid from HuggingFace with no registration, includes a full AMASS/LAFAN1 SMPL retargeting pipeline, implements PPO/GAIL/AMP as single-file JAX algorithms plus DeepMimic-style tracking via MimicReward, and has a procedural RoughTerrain that regenerates a random height field on every reset. The critical caveat is performance, not compatibility: both of its acceleration backends are dead on this hardware. JAX reports only CpuDevice(id=0) and NVIDIA Warp prints "CUDA not enabled in this build", so the 30-core Metal GPU sits completely idle and both MJX and the headline v1.1.0 MjWarp backend fall back to CPU. Measured ceiling is ~5,300 env-steps/s (MJX-CPU, 1024 envs, lax.scan) versus the ~125–180k steps/s the project's own AMP example implies on an RTX 3080 Ti — roughly 24–34x slower, which puts the reference 75M-step AMP run at ~4 hours of pure rollout (more with learning updates) instead of 7–10 minutes. Two further gotchas: v1.1.0 is not on PyPI (a plain `pip install loco-mujoco` silently gives you the year-old 1.0.0), and there is no waypoint/position-navigation goal class — only velocity commands — so multi-waypoint courses must be built yourself.

## Key facts

- VERIFIED ON TARGET MACHINE: loco-mujoco 1.1.0 installed from git master and imported successfully on macOS 26.5 arm64 / Python 3.12.13 (import takes ~36s cold). `ImitationFactory.make("SkeletonTorque", default_dataset_conf=DefaultDatasetConf(["walk"]))` built and stepped without error, auto-downloading walk.npz (35,200 frames) from HuggingFace with no account or registration.
- VERIFIED: `jax.devices()` returns `[CpuDevice(id=0)]` and `jax.default_backend()` is `cpu` with jax 0.11.0 on this M3 Max. No Metal, no GPU.
- VERIFIED: `warp.init()` prints `CUDA not enabled in this build` and lists devices `['cpu']` / `get_cuda_devices() == []` with warp-lang 1.16.0. The v1.1.0 MjWarp backend therefore cannot accelerate anything here.
- Version timeline (GitHub releases atom feed): v0.1.0 2023-12-21, v0.2.0 2024-04-03, v0.2.2 2024-05-05, v0.3.0 2024-05-19, v0.4.1 2024-09-13, v1.0.1 2025-04-18, v1.1.0 2026-03-10.

A 'UNITREE LICENSE' file ships alongside.
- Dataset API: `DefaultDatasetConf`, `LAFAN1DatasetConf`, `AMASSDatasetConf`, `CustomDatasetConf` in loco_mujoco.task_factories. Multiple sources can be mixed in one env.
- AMASS is NOT bundled — requires manual registration/download plus accepting the SMPL license at github.com/vchoutas/smplx. Configured via `loco-mujoco-set-amass-path`, `loco-mujoco-set-smpl-model-path`, `loco-mujoco-set-conv-amass-path`. Needs the `smpl` extra (torch, smplx, joblib, tqdm).
- Full retargeting pipeline is present in loco_mujoco/smpl/retargeting.py: fit_smpl_shape, fit_smpl_motion, to_t_pose, load_retargeted_amass_trajectory, extend_motion, plus robot-to-robot retargeting (motion_transfer_robot_to_robot / retarget_traj_from_robot_to_robot). Per-robot configs in smpl/robot_confs/: Apollo, Atlas, BoosterT1, FourierGR1T2, MyoSkeleton, SkeletonMuscle, SkeletonTorque, Talos, ToddlerBot, UnitreeG1, UnitreeH1, UnitreeH1v2, defaults.yaml.
- Algorithms actually shipped (loco_mujoco/algorithms/): PPOJax (ppo_jax.py), GAILJax (gail_jax.py), AMPJax (amp_jax.py) — all JAX/flax. There is NO VAIL in v1.x (it existed in v0.x via mushroom_rl) and no standalone DeepMimic file: DeepMimic-style tracking is PPO + MimicReward + GoalTrajMimic, shipped as the examples/training_examples/jax_rl_mimic example.
- Reward classes: NoReward, TargetXVelocityReward, TargetVelocityGoalReward, LocomotionReward, TrajectoryBasedReward, TargetVelocityTrajReward, MimicReward. Custom reward classes are a documented extension point, so pure RL is supported alongside IL.
- Terrain classes (loco_mujoco/core/terrain/): Terrain, StaticTerrain, DynamicTerrain, RoughTerrain. RoughTerrain is genuinely procedural — docstring says 'terrain is generated randomly on each reset'; params inner_platform_size_in_meters=1.0, random_min_height=-0.05, random_max_height=0.05, random_step=0.005, random_downsampled_scale=0.4. Defaults are mild (+/-5cm) but configurable.
- Goal classes (loco_mujoco/core/observations/goals.py): Goal, NoGoal, GoalRandomRootVelocity, GoalTrajRootVelocity, GoalTrajMimic, GoalTrajMimicv2. All are ROOT-VELOCITY commands or trajectory-tracking — there is no position/waypoint navigation goal.
- Reference AMP config (examples/training_examples/jax_amp/conf.yaml): env `MjxUnitreeH1`, num_envs 2048, total 75e6 timesteps, DefaultDatasetConf task 'run'. Its README states training takes ~7-10 minutes on an RTX 3080 Ti — i.e. ~125k-180k env-steps/s on that GPU.
- Domain randomization is built in (loco_mujoco/core/domain_randomizer/: base, default, no_randomization). Trajectory comparison metrics (DTW, discrete Frechet) are implemented in JAX via the `metrx` package.
- Gymnasium integration exists: `LocoMujoco-v0` registered pointing at loco_mujoco.core.wrappers.gymnasium:GymnasiumWrapper, so CPU envs can be driven by external PPO implementations (e.g. SB3/CleanRL) instead of the bundled JAX algorithms.
- Zero GitHub issues in the repo match 'mac' or 'apple' (GitHub search API total_count=0 for both). Nobody has reported Apple Silicon success or failure — my benchmarks above are, as far as the public record shows, the first data point.
- Original paper: LocoMuJoCo: A Comprehensive Imitation Learning Benchmark for Locomotion, arXiv:2311.02496 (Al-Hafez et al., 2023). No newer v1.0 paper found.

## Reusable for this project

- SkeletonTorque / SkeletonMuscle — the realistic human-proportioned humanoid the project needs, already built, validated, and paired with retargeted mocap. SkeletonMuscle (92 lower-limb muscles) is a stretch goal for genuinely human-like gait. This alone is months of modelling work avoided.
- The 19 bundled mocap motions per humanoid (walk, run, walkturn, stepinplace1-3, highknee, balance, ...), auto-downloaded from HuggingFace with zero registration — an immediate motion-imitation corpus with no licensing friction. `walk` and `walkturn` map directly onto the walking + multi-waypoint-turning goals.
- AMPJax (loco_mujoco/algorithms/amp_jax.py) — a working single-file AMP implementation wired to these envs. This is precisely the AMP-style motion imitation the project specifies; do not reimplement it.
- PPOJax with save/load checkpointing (new in v1.1.0) — the PPO backbone, already integrated with the vectorized env API and checkpointable for long overnight CPU runs.
- MimicReward + GoalTrajMimic/GoalTrajMimicv2 + TrajectoryBasedReward — a complete DeepMimic-style phase-tracking reward stack, reusable as the alternative or complement to AMP.
- RoughTerrain — procedural random height field regenerated every reset, with tunable amplitude/step/downsample. This is the procedural-terrain requirement essentially done; the difficulty curriculum is just scheduling random_min_height/random_max_height.
- The SMPL/AMASS retargeting pipeline (fit_smpl_shape, fit_smpl_motion, to_t_pose) plus the 12 per-robot YAML configs — if you ever want your own mocap or a custom body, this is the hard part already solved. Robot-to-robot retargeting lets you move motions between the human skeleton and H1/G1 without redoing mocap.
- The trajectory-comparison metrics (DTW, discrete Frechet, via `metrx`) — ready-made quantitative gait-similarity measures for the 'human-like gait' success criterion, which is otherwise hard to score.
- The GymnasiumWrapper / `LocoMujoco-v0` registration — an escape hatch letting you drive the CPU MuJoCo envs from your own PPO (or SB3/CleanRL) with multiprocess vectorization across the 10 P-cores, sidestepping the JAX-CPU ceiling entirely. Worth benchmarking against MJX-CPU: 10 processes x ~1,140 steps/s could plausibly beat the ~5,300 steps/s MJX-CPU ceiling.
- The domain randomizer and the observation/goal/reward class hierarchy — clean, documented extension points. The missing multi-waypoint navigation can be added as a new Goal subclass rather than a fork.
- examples/speed_test.py and the four training examples (jax_rl, jax_gail, jax_amp, jax_rl_mimic) — ready-made harnesses to calibrate Phase 0 benchmarking against.

## Blockers

- NO CUDA => MJX-JAX runs on the CPU backend only. Verified: jax 0.11.0 reports [CpuDevice(id=0)]. The 30-core Metal GPU contributes nothing.
- The v1.1.0 flagship MjWarp backend is useless here. NVIDIA Warp on macOS arm64 reports 'CUDA not enabled in this build' with only a 'cpu' device, so `use_mjwarp=True` cannot deliver its advertised 30% speedup. mujoco-warp's own docs say it 'requires an NVIDIA GPU for fast simulation but supports CPU for development and debugging' — debugging is all you get.
- jax-metal is effectively dead and cannot rescue this: last release 0.1.1 on 2024-10-08 (~22 months stale), and it requires jax>=0.4.34/jaxlib>=0.4.34 against the jax 0.11.0 that loco-mujoco 1.1.0 resolves to. Do not plan around it.
- Throughput is ~24-34x below the hardware the project's own examples are tuned for. The jax_amp reference config (2048 envs, 75M steps) is a 7-10 minute job on an RTX 3080 Ti; at the ~5,300 steps/s I measured it is ~4 hours of pure rollout on this M3 Max, and more once PPO/AMP network updates (also CPU-bound JAX) are counted. Overnight-feasible, not interactive.
- v1.1.0 is NOT on PyPI (pypi.org/pypi/loco-mujoco/1.1.0/json => 404). `pip install loco-mujoco` silently installs 1.0.0 from 2025-04-17, which pins mujoco==3.2.7 and numpy<2.0 and will fight the rest of a modern stack. You must install from git and pin a commit SHA.
- No multi-waypoint navigation exists. Every Goal class is a root-velocity command or a trajectory-mimic target; there is no position-goal/waypoint-course machinery. The project's multi-waypoint course requirement must be written from scratch on top of GoalRandomRootVelocity.
- AMASS requires registration (amass.is.tue.mpg.de) plus accepting the SMPL license at github.com/vchoutas/smplx, and pulls a torch + smplx + joblib extra. Only the Default and LAFAN1 datasets are friction-free.
- Dependency hygiene risk: the resolution pulls `tfp-nightly==0.26.0.dev20260812` (a TensorFlow Probability NIGHTLY, via distrax) and `loco-mujoco-models` straight from a git HEAD. Both are floating targets that can break a build overnight; pin them in uv.lock.
- Known open bug directly on the path this project would take: issue #90 (open, 2026-03-25) 'OOM issue during DeepMimic Imitation Learning Example (jax rl mimic)' reports memory escalating until all 64GB of CPU RAM is consumed. I reproduced a related pathology: a naive Python-loop rollout at 256 envs collapsed to 71 steps/s from JAX async-dispatch queueing; rewriting with jax.lax.scan fixed it (3,776 steps/s). On a CPU backend you must keep rollouts inside scan/jit.
- Other relevant open issues: #88 abnormal foot behavior with SkeletonTorque on AMASS (2025-12-18), #87 evaluation error using MjxSkeletonMuscle (2025-11-18), #89 SMPLH_Parser import failure (2026-02-03), #80 hard package conflicts when running retargeting.py (2025-08-01).
- master has been stale for 5 months while fixes accumulate unmerged in dev and in open PRs #94-#97 — pinning master means shipping known-unfixed bugs; pinning dev means shipping untagged code.

## Performance evidence

- MEASURED BY ME on the target M3 Max (SkeletonTorque, 27 act / 65 obs, random actions, rollout only, no policy or learning updates): CPU MuJoCo single env = 1,142 env-steps/s (3,000 steps in 2.63s).
- MEASURED BY ME, MJX on JAX-CPU with jax.lax.scan (the pattern the shipped algorithms use): 256 envs = 3,776 steps/s (12,800 env-steps in 3.39s); 1024 envs = 5,321 steps/s (51,200 env-steps in 9.62s). Scaling saturates around 5-6k steps/s.
- MEASURED BY ME, MJX on JAX-CPU with a naive Python step loop (async dispatch, NOT scan): 64 envs = 1,793 steps/s, 128 envs = 2,468 steps/s, 256 envs = 71 steps/s. The cliff at 256 is a dispatch-queue/memory pathology, not steady-state cost — the same config under lax.scan hits 3,776 steps/s. Treat the loop numbers as a warning about how to write the rollout, not as the backend's real speed.
- MEASURED BY ME: JAX compile overhead is non-trivial on CPU — scan compile + first rollout was 10.9s at 256 envs and 14.8s at 1024 envs; cold `import loco_mujoco` took 36s; MJX env construction ~11s.
- PUBLISHED (project's own examples/training_examples/jax_amp/README.md): AMP on MjxUnitreeH1, 2048 envs, 75e6 timesteps, '~7-10 minutes on an RTX 3080 Ti' => ~125,000-180,000 env-steps/s. Ratio to my measured 5,321 steps/s = ~24-34x slower on this Mac.
- DERIVED: at 5,321 steps/s the 75M-step reference AMP run is ~14,100s (~3.9 hours) of rollout alone. Add CPU-bound actor/critic/discriminator updates and budget roughly 6-12 hours wall-clock. This is an estimate, not a measured end-to-end training run.
- PUBLISHED (MuJoCo docs, mjx.html): 'Simulating a single scene, MJX-JAX can be 10x slower than MuJoCo, which has been carefully optimized for CPU' — consistent with my finding that 64 MJX-CPU envs only barely beat one native CPU MuJoCo env.
- PUBLISHED (MuJoCo docs, mjx.html): 'MJX-JAX runs on: Nvidia and AMD GPUs, Apple Silicon, and Google Cloud TPUs.' NOTE: this claim is misleading for planning purposes — 'Apple Silicon' here means the XLA CPU backend on arm64, which is exactly what I measured. There is no working Metal GPU path.
- NO published Apple Silicon benchmark for LocoMuJoCo exists anywhere I could find; the repo has zero issues mentioning mac/apple/arm.
